## 0. 먼저 — 오늘 잰 값이 설계 두 개를 바꿉니다

신규 5축 팔(arm_v2)을 본체 arm_mount 에 붙인 상태로 전수 조사했습니다
(`scripts/14_reach_map.py`, 관절 격자 2° · 자세 181만 개).
joint5 는 툴 축 롤이라 위치에 영향이 없어 닫힌 형태로 전수 계산이 됩니다.

### ★ 제약 1 — 쓰레기통을 본체 상판에 두면 팔이 못 닿습니다

| 툴 자세 | 도달 최대 높이 (본체 좌표) |
|---|---|
| 아래 ±30° — 똑바로 떨구기 | **428 mm** |
| 아래 ±45° | 483 mm |
| 아래 ±60° — 기울여 떨구기 | 541 mm |
| 자유 (툴 방향 무시) | 657 mm |

**본체 높이는 831 mm 입니다.** 상판에 쓰레기통을 얹으면 400 mm 가까이 모자랍니다.

> **권고 — 개구부를 z ≤ 400 mm 에 두세요.** 본체 앞면이나 옆면의 낮은 위치입니다.
> z=400 mm 에서 툴을 아래로 향한 채 닿는 범위는 본체 x +2 ~ +627 mm 입니다.
> 개구부를 크게 만들면(∅150 mm 이상) 정렬 오차를 흡수해서 성공률이 크게 오릅니다.

### ★ 제약 2 — 그리퍼 개구 57 mm 가 품목 선정의 1차 필터입니다

실측 스윕 56점 피팅 기준 **개구 0.5 ~ 57.1 mm** (`gripper_map.py`).

| 품목 | 폭 | |
|---|---|---|
| 빨대 | 6 mm | ✅ |
| 페트병 목 | 25 mm | ✅ |
| 페트병 뚜껑 | 30 mm | ✅ |
| 나무토막 | 40 mm | ✅ |
| **500 ml 페트병 몸통** | 65 mm | ❌ 개구 초과 |
| **알루미늄 캔 몸통** | 66 mm | ❌ 개구 초과 |
| **종이컵 입구** | 80 mm | ❌ 개구 초과 |

캔과 페트병은 **몸통을 가로로 잡을 수 없습니다.** 목이나 뚜껑을 잡거나,
눌러 찌그러진 상태로 잡거나, 품목에서 빼야 합니다. 데이터를 모으기 전에 정하세요.

### 바닥 작업영역 — 기존 문서 숫자는 폐기하세요

| | 옛날 팔 | **신규 팔 (arm_v2)** |

물체는 **본체 앞쪽 2,872 cm²** 안에 뿌리는 것이 자연스럽습니다.

> ⚠️ 가정 — base_link 가 arm_mount 에 rpy 0 으로 붙습니다. 신규 팔의 장착

## 1. ★ 태스크를 둘로 쪼개세요

이게 이 로드맵에서 제일 중요한 판단입니다.

| | A. 집기 (Pick) | B. 넣기 (Place) |
|---|---|---|
| 대상 위치 | 매번 다름 | **본체에 고정 — 항상 같은 좌표** |
| 시각 의존 | 절대적 | 거의 없음 |
| 난이도 | 높음 | 낮음 |
| 처음엔 | **학습** | **고정 궤적 스크립트** |

쓰레기통이 로봇 몸에 붙어 있다는 건 **B 가 사실상 공짜**라는 뜻입니다.
물체를 쥔 뒤에는 언제나 같은 관절각 시퀀스를 재생하면 됩니다.

**공부용이라면 A 만 학습하고 B 는 스크립트로 시작하세요.** 성공률이 훨씬 빨리
올라오고, 실패했을 때 원인이 "집기"인지 "넣기"인지 헷갈리지 않습니다.
A 가 안정되면 전체를 end-to-end 로 다시 학습해 통합합니다.

## 2. 측정 리스트

체크박스는 그대로 진행표로 쓰시면 됩니다.
**A·C·D·E·F 는 실물 ACT 에 필요하고, B 는 RL/시뮬로 갈 때만 필요합니다.**

### A. 좌표 · 영점 — 제일 먼저. 이게 틀리면 나머지가 전부 무의미

- [ ] 관절별 **영점 오프셋** (URDF 0 자세 ↔ 서보 0 위치)
- [ ] 관절별 **회전 부호** — ★ joint5 축이 `(0,0,-1)` 입니다
- [ ] **기어비/스케일** — 지령 1 rad 이 실제로 몇 rad 인가
- [ ] **가동범위 실측** vs URDF 리밋 대조
- [ ] 홈 자세 재현성 — 전원을 껐다 켜도 같은 자세로 오는가

> **방법** 한 관절씩, 손으로 잡을 수 있는 속도로. URDF 0 자세를 화면에 띄우고
> 실물 사진과 겹쳐 봅니다. 우리는 손목 롤 축을 X 로 잘못 잡고도 **한쪽으로는
> 그럭저럭 돌아서** 한참 못 찾았습니다. 부분적으로 그럴듯한 오류가 제일 오래 삽니다.

### B. 팔 물성 — RL 입장료 (실물 ACT 에는 불필요)

- [ ] **링크별 질량** (저울) — CAD 값 금지. 팔 CAD 6.72 kg → 실측 2.32 kg (2.9배 과대)
- [ ] **정지마찰 / 동마찰** — 무부하로 지령을 서서히 올려 움직이기 시작하는 값
- [ ] **백래시** — 같은 목표를 정방향/역방향으로 접근했을 때 실제 위치 차
- [ ] **스텝 응답** — 계단 입력의 상승시간·오버슈트·정착시간 → Isaac stiffness/damping 정합값
- [ ] **최대 속도·토크** 실측
- [ ] **전 구간 지연** — 지령 송신에서 실제 움직임 시작까지

> 젯슨 팀이 실기에서 `velocity_scale` 이 속도가 아니라 사실상 **토크 상한**으로
> 작동한다는 것, 마찰이 큰 팔은 scale 0.1 에서 아예 안 움직인다는 것을 찾았습니다.
> 시뮬에 마찰을 안 넣으면 이 구간이 통째로 안 보입니다.

### C. 그리퍼

- [x] 개구 ↔ 서보각 — 실측 56점 피팅 완료 (`gripper_map.py`)
- [ ] **파지력 (N)** — 개구별로. 가벼운 쓰레기라 과하면 찌그러집니다
- [ ] **미끄러지기 시작하는 무게** — 품목별
- [ ] 조 표면 재질 / 고무 패드 유무
- [ ] 완전히 닫았을 때 실제 개구 (피팅은 −0.3 mm 로 나옵니다 = 접촉)

### D. 카메라 — ACT 의 입력이라 여기가 제일 중요

- [ ] **실측 화각** — 자를 알려진 거리에 놓고 역산. 스펙 시트보다 실측이 우선
- [ ] **장착 위치·각도 실측** (본체 좌표) → URDF 와 일치하는지
- [ ] **내부 파라미터·왜곡** — 체커보드 캘리브레이션
- [ ] **D435i RGB 광학중심 오프셋** — 62번 §4 로 물었고 아직 회신 없음
- [ ] **프레임 지연**
- [ ] ★ **자동노출 / 자동 화이트밸런스 끄기** — 켜져 있으면 같은 장면이 매번 다르게
      찍혀서 정책이 조명 변화를 물체 신호로 오인합니다. **고정하고 값을 기록하세요**
- [ ] **본체 카메라 기울기 확정** ← 아직 미정. 브래킷 만들기 **전에** 정해야 합니다

> 정면(0°)이면 바닥 작업영역이 **0% 보입니다.** 30°→16.8 · 50°→64.2 · 60°→85.6 ·
> 65°→92.5%. 렌더로는 50° 가 60° 보다 나아 보였습니다(60°에선 본체가 화면 절반).

### E. 태스크 · 환경

- [ ] **쓰레기통 개구부** 위치·크기 (본체 좌표) — §0 제약 안에서
- [ ] **바닥 재질 목록** — 장판/마루/타일/카펫 등. 각각 사진과 반사 특성
- [ ] **재질별 물체-바닥 마찰** — 미끄러지면 밀려서 못 잡습니다
- [ ] **쓰레기 품목표** — 품목별 무게·크기·강성(딱딱/무름)·표면
- [ ] **조명 조건 범위** — 낮/밤/형광등/자연광 중 어디까지 감당할 것인가
- [ ] **물체 초기 위치 분포** — 어느 영역에 어떻게 뿌릴 것인가

### F. 시스템

- [ ] 제어 루프 **실제 주기와 지터** (목표 30 Hz)
- [ ] **UDP 손실률·지연** — 실물 네트워크에서
- [ ] **저장 대역폭** — 30 Hz × 카메라 2대 × 720p 를 감당하는가
- [ ] 에피소드 한 개의 디스크 용량 → 총 몇 GB 가 될 것인가

## 4. 로드맵

### Phase 0 — 실물이 움직이게 한다 ← **지금 여기서 막혀 있습니다**
- 젯슨 실물 모터 드라이버 (이 저장소에 없음 — 젯슨 담당 영역)
- 측정 A (영점·부호·스케일)
- 그리퍼 통로 — Mac 쪽은 송신 시작함(`grasp` 상시 전송), 수신 쪽만 남음
- **✅ 검증** VR 로 팔 5축 + 그리퍼가 실물에서 의도대로 움직인다

### Phase 1 — 하드웨어 확정 (되돌리기 제일 비쌈)
- 본체 카메라 기울기 결정 → URDF 갱신 → **실물도 같은 각도로 장착**
- 쓰레기통 위치·크기 확정 (§0 제약)
- 팔 장착 인터페이스 확정 → 도달 범위 재계산
- **✅ 검증** 카메라 2대가 실물에 달리고 §D 실측이 URDF 와 일치

### Phase 2 — 측정 (C · D · E · F)
- **✅ 검증** 측정표가 채워지고 품목 목록이 개구 57 mm 필터를 통과

### Phase 3 — 태스크 · 데이터 스키마 정의
- 에피소드 경계(언제 시작/끝), **성공 판정 기준**
- 관찰(이미지 2 + 관절각 5 + 그리퍼 1) / 행동(관절각 5 + 그리퍼 1)
- **태스크 문장** 기록 — VLA 를 나중에라도 할 생각이면 지금 넣으세요.
  비용은 0 이고, 안 넣으면 수백 에피소드를 다시 모아야 합니다
- **✅ 검증** 스키마 문서 한 장. 젯슨/시뮬 양쪽이 같은 걸 본다

### Phase 4 — 기록 계층 + 파일럿 10 에피소드
- 어디서 기록할 것인가 (젯슨 로컬 vs Mac 전송) 결정
- **✅ 검증** 10개를 lerobot 데이터셋으로 저장 → 되읽어 재생 → 원본과 일치

> 파일럿을 건너뛰지 마세요. 스키마 실수는 **수백 에피소드를 모은 뒤에** 드러납니다.

### Phase 5 — 본 수집
- 품목 × 바닥 × 위치 조합. 1단계 품목 3~4종 × 바닥 2~3종부터
- 규모 **태스크당 50 에피소드**부터 (ALOHA 논문 기준). 부족하면 늘립니다
- **✅ 검증** 조합별로 고르게 모였는가 (한 조합에 쏠리면 그것만 배웁니다)

### Phase 6 — ACT 학습 + 실물 평가
```bash
lerobot-train --dataset.repo_id=<계정>/<데이터셋> --policy.type=act \
  --output_dir=outputs/train/trash --policy.device=cuda
```
- 정책이 **VR 컨트롤러 자리에** 들어갑니다. 안전계층은 그대로 뒤에 남습니다
- **✅ 검증** 성공률 숫자. 첫 판에 20~40% 나오면 정상 출발입니다

### Phase 7 — 실패 분석 → 데이터 보강 ← **대부분 여기서 해결됩니다**
- 실패를 유형으로 나눕니다 (못 봄 / 못 닿음 / 놓침 / 넣다가 떨어뜨림)
- 제일 많은 유형만 골라 데이터를 더 모읍니다
- **✅ 검증** 성공률이 올라간다. 안 오르면 그때 Phase 8

### Phase 8 — (필요할 때만) 시뮬 정합 → RL / VLA
진입 조건은 §5 에.

## 5. 강화학습으로 넘어가는 조건

RL 은 코스의 다음 단계가 아니라 **필요가 생겼을 때** 하는 것입니다.

**넘어갈 신호**
- 데이터를 늘려도 성공률이 천장에 걸림
- 사람이 시범을 못 보이는 동작 (아주 빠르거나, 힘 조절이 섬세하거나)
- 조금만 바뀌어도 매번 데이터를 다시 모아야 함

**입장료** — 전부 §2-B 와 §2-E 의 실측입니다
1. 시뮬이 실물과 같아야 함 (마찰·질량·서보 응답·지연)
2. 보상 함수 — "집었다"를 숫자로. RL 실패의 대부분이 여기
3. 대규모 병렬 환경 (Isaac Lab)
4. 도메인 랜덤화 범위 — 추측이 아니라 실측한 갭에서

> **RL 은 시뮬에서만 합니다.** 수만 번의 시행착오를 실물로 하면 팔이 부서집니다.

### ★ 입장료를 미리 벌어두는 법 — 추가 비용 거의 0

영점 교정이 끝나면 **같은 지령을 실물과 시뮬에 동시에 쏠 수 있습니다.**
프로토콜이 같고 포트만 다릅니다.

```
맥북 ─┬─ 5005 ─▶ 젯슨  ─▶ 실물 ─▶ 관절각 ┐
      └─ 5015 ─▶ 브릿지 ─▶ 시뮬 ─▶ 관절각 ┴─ 차이 = 갭 (숫자)
```

**Phase 5 에서 실물 데이터를 모으는 그 시간에 시뮬로도 같이 쏘면**, 마찰·게인·지연
정합값이 공짜로 쌓입니다. 나중에 필요해졌을 때 입장료의 절반 이상이 이미
