 A-4  재무장 관문                                        합의 2026-08-07
--------------------------------------------------------------------------------
  세션이 바뀌거나 링크가 끊기면 **HOLD 또는 DISABLED 를 한 번 받기 전까지
  RUN 을 거부**한다. 받는 쪽이 강제한다. "Mac 이 예의 바르게 굴 것"에 기대지
  않는다.

  임계는 stale(100ms)이 아니라 **lost** 에서 건다. stale 에서 내리면 30Hz
  기준 3프레임 손실마다 클러치를 다시 잡아야 해서 조종이 불가능해진다.

 A-9  HOLD 는 진입 시 1회만 목표를 잡는다              합의 2026-08-07
--------------------------------------------------------------------------------
  HOLD 로 들어가는 **그 순간 한 번** 목표를 잡는다. 매 프레임 현재 위치로
  다시 잡으면 안 된다.

  왜 — PD 드라이브에서 매 프레임 target 을 q 로 덮으면 (target − q) 가 항상
  0 이라 **복원 토크가 사라진다.** 감쇠항만 남아 중력이 계속 이긴다.
  stiffness 를 아무리 넣어도 HOLD 중에는 무효가 된다.

  실측 (Isaac 브릿지, 수정 전) — HOLD 를 30Hz 로 계속 보내는 동안
       5s  joint2 -26.0°  joint4 +23.7°
      15s        -67.0°         +55.7°
      72s        -83.4°         +50.0°  ← 바닥에 닿아 정지
      HOLD 지령과 최종 이격 **134.2°**. link=ok 20ms 로 끝까지 정상이었다.
  수정 후 90초 유지 → 최대 이동 0.36°.

  ★ 실물에도 그대로 위험하다. 05_teleop_sim.py 가 종료할 때 DISABLED 가 아니라
    HOLD 로 나가는 것도 "소자하면 팔이 중력으로 떨어진다" 때문이다.
    천천히 주저앉는 HOLD 는 같은 사고가 느리게 일어나는 것이다.

  전이별 목표값 (13_JETSON_REPLY2 §1-A 에서 이미 정한 것)
      DISABLED → HOLD   현재 실제 q      (처져 있는 데서 안 튀게)
      RUN      → HOLD   마지막 수락 q    (뒤처진 위치를 굳히지 않게)
      워치독 freeze     마지막 수락 q

  검증 — 실물 갈래 참조 구현(jetson_sim.py)은 이미 이 규칙을 지킨다.
  회귀 테스트 `test_hold_latches_target_once_on_entry` 로 못박았다.

 A-11  지령에 속도(dq)를 싣는다                         합의 2026-08-07
--------------------------------------------------------------------------------
      "dq": [0.5, -0.3, 0.0]                지령 패킷 (없으면 필드가 빠짐)

  왜 — 임피던스 제어 토크는  τ = kp·(p_des−p) + kd·(v_des−v) + τ_ff  인데,
  인터페이스가 q 만 받으면 구현체가 **v_des 를 알 수 없어 0 을 넣는다.**
  그러면 kd 항이 `kd·(0−v)` 가 되어 **로봇이 자기 움직임에 제동을 건다.**

  실측 (젯슨 실기) — kd 2.0, 지령속도 1.131 rad/s → **-2.26 N·m**
  이 팔의 브레이크어웨이(0.5~0.8 N·m)보다 큰 제동이었다.

  ★ MockBackend 는 v_des 를 안 쓰므로 **시뮬에서는 절대 안 드러난다.**
    실물에서 만나기 전까지 아무도 몰랐다.

  MotorBackend 인터페이스도 `write_positions(q, dq=None)` 로 넓혔다.
  dq 를 안 주면 구현체가 차분으로 구해도 되지만, Mac 은 정확한 값을 안다.

 A-13  velocity_scale 은 토크 상한이기도 하다           확인 2026-08-07
--------------------------------------------------------------------------------
  합의라기보다 **함정 기록**이다. 다음 사람이 같은 곳에서 시간을 태우지 않게.

      max_step = max_velocity × velocity_scale × dt
      max_lag  = max(max_step × 5, 0.05)
      → 오차가 max_lag 을 못 넘음 → τ ≈ kp × 오차
      ∴ 최대 토크 ∝ velocity_scale

          scale   max_lag   도약    kp=100 최대토크
          0.1     0.0628    3.6°       6.3 N·m
          0.3     0.1885   10.8°      18.9 N·m

  ★ **안 움직이면 kp 가 아니라 velocity_scale 을 먼저 의심할 것.**
    실기에서 kp 를 8→100 으로 12배 올려도 그대로였고 scale 한 번에 해결됐다.
  ★ 반대로 올리면 정지→출발 도약이 커진다. 맞바꾸기다.
  ※ 텔레옵 스케일(사람 손 → 로봇 변위 배율)과는 **다른 변수**다.


 A-14  v_des 는 '클램프된 지령'의 차분을 쓴다             합의 2026-08-07
--------------------------------------------------------------------------------
  받는 쪽이 임피던스 제어(τ = kp·Δp + kd·Δv + τ_ff)를 쓸 때,
  **v_des 에 Mac 의 dq 를 그대로 넣으면 안 된다.**

      v_des = (클램프된 지령 − 직전 클램프된 지령) / **공칭 dt**

  왜 — Mac 의 dq 는 안전계층을 통과하기 **전**의 의도다. 안전계층이 위치를
  클램프하면 낼 수 있는 속도도 깎인다. v_des 에 깎이기 전 값을 넣으면

      kd × (의도 − 실제) = 2.0 × (3.0 − 1.131) = +3.74 N·m

  만큼 계속 밀어서 **안전계층이 깎은 만큼을 kd 가 되밀어준다.**
  관절이 클램프된 지령보다 kd·Δv/kp 만큼 앞서 달리고(위 값이면 0.037 rad),
  그만큼 관절 한계 마진(0.05 rad)을 잡아먹는다.

  ※ 벽시계가 아니라 **공칭 dt** 로 나눈다. 안전계층은 매 틱 정확히 max_step
    만큼만 움직이므로 이 값이 정의상 정확하고 루프 지터가 안 섞인다.
    (자기 지령을 차분하는 것이라 수신 지터와도 무관하다)


 A-15  마찰 보상 판단에 '클램프된 지령 속도'를 쓰면 안 된다   확인 2026-08-07
--------------------------------------------------------------------------------
  함정 기록이다.

  정지마찰로 실제가 안 움직이면
      → 이격 제한이 지령을 실제 + max_lag 에 **고정**
      → 지령이 더 안 나아감 → **클램프된 dq = 0**
      → 마찰 보상이 정확히 필요한 순간에 꺼진다

  실측 (velocity_scale 0.3, 막힌 관절에 계속 지령)
      틱 3~5   클램프 dq 1.131 rad/s      오차 쌓이는 중
      틱 10~   클램프 dq **0.00000**      오차 0.1885 에 고정
                                          ← 여기가 보상이 필요한 구간

  ★ "실제 속도로 판단하면 안 된다" 까지는 맞지만, **클램프된 지령 속도도
    같은 함정**이다. 살아남는 신호는 둘뿐이다.

      위치 오차   정지마찰 구간에도 max_lag 에 붙어 유지된다
      Mac 의 dq   클램프 전이라 사람이 움직이는 한 0 이 아니다

  → 방향은 위치 오차로, "의도가 있는가" 는 Mac dq 로 판단한다.


 A-16  팔 식별자가 있으면 **그것만이 권위다**              합의 2026-08-08
--------------------------------------------------------------------------------
  A-10 을 명확히 한다. 식별자와 관절 수를 **AND 로 걸지 않는다.**

      robot 필드 있음  →  이름만 본다. 관절 수는 "모자란가" 만 본다
      robot 필드 없음  →  관절 수를 그대로 본다 (구버전 하위호환)

  왜 — 받는 쪽은 팔보다 **많은** 관절을 보낼 수 있다. Isaac 은 팔 5 + 손 12
  = 17개를 보내고 Mac 은 앞의 5개만 쓴다 (doc 18 §2.3, read_positions 가
  q[:n] 으로 자른다). AND 로 걸면 이 정상 구성이 **영원히 무장하지 못한다.**

  ★ 실제로 그 상태로 Isaac 갈래가 통째로 막혀 있었다 (20_ISAAC M-10).
    지령이 아예 안 나가는데 mode 는 HOLD, seq 는 증가, trip 도 정상이라
    "설정 문제인가 네트워크 문제인가" 로 한참 헤맸다.

  ★ 넘치는 것은 정상이고 **모자란 것은 막는다.** read_positions() 가 짧은 q 를
    0 으로 채우므로, 통과시키면 없는 관절을 "0 도에 있다" 고 믿고 지령한다.

  ★ 식별자가 없을 때는 != 를 유지한다. 식별자가 없으면 "팔+손이라 긴 것" 과
    "아예 다른 팔" 을 구별할 방법이 없고, 조용히 엉뚱한 팔을 움직이는 쪽이
    더 나쁘다. 길게 보내는 받는 쪽은 **robot 필드를 실어 보내면 된다.**


 A-17  상태에 quest 연결 여부를 싣는다                     합의 2026-08-08
--------------------------------------------------------------------------------
      "quest": "ok" | "lost" | "waiting"        Mac → 브라우저 상태

  "한 번도 안 붙음(waiting)" 과 "붙었다가 끊김(lost)" 은 완전히 다른 상황인데
  예전에는 둘 다 아무 표시가 없었다. 헤드셋을 벗거나 슬립에 들면 WebXR 세션이
  끊기는데, 조종자에겐 "멀쩡해 보이는데 안 움직인다" 로만 보인다.

  실측 (시뮬 담당) — 끊긴 뒤 **37분간 로그 무음**. 사람이 seq 증가율
  (30Hz 정상 / 9.7Hz idle) 로 진단하고 있었다. 그렇게 두면 안 된다.

  · 터미널에 2초마다 "⚠️ Quest 연결 끊김 — [Start XR] 을 다시" 출력
  · 대시보드 카드로 표시 (lost 는 빨강)
