 1-1. 새 세션이 HOLD 로 안 내려감
--------------------------------------------------------------------------------
  저희 재현 (velocity_scale=1.0, 세션2 첫 패킷부터 mode=RUN)

      수정 전   세션1  state=RUN  q=[ 0.298 -0.200]
                세션2  state=RUN  q=[ 0.900  0.600]   기대 HOLD   ❌
      수정 후   세션1  state=RUN  q=[ 0.300 -0.200]
                세션2  state=HOLD q=[ 0.300 -0.200]               ✅

  원인은 지적하신 그대로입니다. 세션 변경에서 `state` 만 HOLD 로 바꿔놓고
  같은 패킷의 모드 전이로 흘러내려가 다시 RUN 으로 올라갔습니다.
  **상태를 바꾸는 것만으로는 못 막습니다. 관문이 필요합니다.**

  수정: `_await_rearm` 플래그. 세션이 바뀌면 세우고, **HOLD 또는 DISABLED
  패킷을 한 번 받기 전까지 RUN 을 거부**합니다. 거부한 횟수는
  `stats["rearm_blocked"]` 로 셉니다.

  ★ 테스트가 못 잡은 이유도 지적하신 그대로입니다. 기존 테스트가
    `be2.hold()` 를 먼저 불러 "예의 바른 Mac" 만 검증했습니다.
    새 테스트는 **원시 UDP 로 RUN 만 쏩니다** (`test_new_session_refuses_run_until_hold`).

 1-2. 링크 복구 시 재무장 없이 이어감
--------------------------------------------------------------------------------
  저희 재현 (freeze 0.1 / lost 0.5 / trip 3.0, 1.5초 두절 후 복구)

      수정 전   두절 후  state=RUN   stage=lost  rx_age=1.52s
                복구 후  q [0.193 -0.100] → [0.900 0.600]   이동 0.995 rad  ❌
      수정 후   두절 후  state=HOLD  stage=lost  rx_age=1.52s
                복구 후  이동 0.000 rad                                    ✅

  ★ 다만 **임계를 stale 이 아니라 lost 로 잡았습니다.** 이유가 있습니다.

    stale(100ms)에서 내려오면, 30 Hz 기준 **연속 3프레임만 빠져도** 사람이
    클러치를 다시 잡아야 합니다. 그 정도 손실은 무선에서 일상적이라 조종이
    사실상 불가능해집니다. 반면 lost(500ms = 15프레임 연속 손실)는
    "진짜 끊겼다"고 볼 수 있는 구간입니다.

    그쪽 §5-2 실측이 이 선택을 뒷받침합니다. **3000패킷 중 100ms 초과 0개,
    최대 37.7ms.** 즉 500ms 임계는 정상 링크에서 한 번도 안 걸립니다.
    USB 직결(1.16ms)이면 더욱 그렇습니다.

    단계별 동작을 이렇게 확정했습니다.

        stale (100ms~) 지령 동결. state 는 RUN 유지. link="stale" 로 알림.
        lost  (500ms~) **state := HOLD + 재무장 요구.** 토크는 유지.
        trip  (설정)   TRIP.

  ★ (a) "state 가 링크 끊김을 안 알린다" — 이건 별도로 고쳤습니다.
    **state 에 통신 상태를 섞지 않고 `link` 필드를 새로 뒀습니다.**

        "state": "RUN"        모터 상태머신   (IDLE|HOLD|RUN|TRIP)
        "link":  "lost"       통신 건강도     (ok|stale|lost)
        "await_rearm": true    RUN 을 거부 중인가

    두 축은 직교해야 합니다. state 하나에 통신까지 실으면 모터가 무슨
    상태인지 알 수 없게 되고, 반대로 하면 대시보드가 "정상 추종 중"으로
    보이는 동안 링크가 죽어 있을 수 있습니다.

  ★ `test_watchdog_freezes_before_tripping` 이 freeze 구간에서 RUN 을 단언한
    것은 **의도가 아니라 제 구현을 그대로 굳힌 것**이었습니다.
    지적하신 대로 문구(§6-3)에 맞췄고, 테스트를 stale/lost/trip 3구간으로
    나눠 다시 썼습니다.

 1-3. dt 와 rate_hz 어긋남
--------------------------------------------------------------------------------
  저희 재현 (velocity_scale=0.1 → 한계 0.377 rad/s, 벽시계 총 이동량 기준)

      수정 전   rate_hz= 30  dt=1/30 →  0.198 rad/s          ✅
                rate_hz=100  dt=1/30 →  0.606 rad/s   1.6배  ❌
                rate_hz=500  dt=1/30 →  2.848 rad/s   7.6배  ❌
      수정 후   motor_hz= 30 →  0.238 rad/s   ✅
                motor_hz=100 →  0.229 rad/s   ✅
                motor_hz=500 →  0.241 rad/s   ✅

  ※ 저희 배수(7.6)가 그쪽(13.5)보다 작은 건 측정 기준 차이입니다. 저희는
    1초 벽시계 총 이동량(평균), 그쪽은 순간 최대로 보입니다. 결론은 같습니다.
    **"빠른 기계일수록 더 뚫린다"** 는 관찰이 특히 정확합니다.

  수정: 제안하신 구조 그대로 넣었습니다.

      UDP 30Hz ─> SafetyLayer(control_hz = 1/dt) ─> 보간기(motor_hz) ─> 모터
                  여기서만 제한                     안전계층 출력 사이만 메움

  · 제어 루프를 상태 송신 루프에서 **분리**했습니다 (`_control_loop`).
    안전계층은 `control_hz = 1/dt` 로만 돕니다.
  · 보간기(`_interp_loop`)는 **안전계층 뒤**입니다. 이미 제한된 두 점 사이만
    지나므로 구조적으로 한계를 넘을 수 없습니다.
  · `FakeJetson(motor_hz=500)` 로 쓰시면 됩니다. 참조 구현에 들어있습니다.

  ★ 12번 문서 §1-Q6 의 "30Hz 받아 500Hz 보간" 계획을 이 구조에 얹으면
    안전합니다. 그쪽이 지적하신 함정이 구조적으로 막힙니다.

 3. §8-C 워치독 TRIP 3초 → 1초
================================================================================

  **동의합니다.** 근거로 드신 실측(3000패킷 중 100ms 초과 0개)이 3초의 전제를
  무너뜨립니다. 원래 3초는 "핫스팟은 0.5초 끊김이 일상적" 이라는 가정에서
  나온 값이었고, 그 가정이 틀렸습니다.

  다만 §1-2 대로 **lost(500ms)에서 이미 HOLD 로 내려가 팔이 멈추므로**,
  TRIP 값 자체의 위험도는 크게 낮아졌습니다. 3초 동안 계속 움직이던 문제는
  사라졌습니다.

  값은 전부 설정으로 빠져 있습니다 (`SafetyLimits`).

      watchdog_freeze_s     0.10   지령 동결
      watchdog_linklost_s   0.50   RUN 에서 내려옴 + 재무장 요구
      watchdog_s            3.00   TRIP        ← 여기를 1.0 으로

  **실제 링크로 30분 이상 돌려보고 확정하자**는 제안에 동의합니다.
  그때까지는 1.0 으로 두고 시작하시죠. 저희 쪽 기본값도 맞추겠습니다.

 4. §8-D 네트워크 — USB 직결로 갑시다
================================================================================

  **좋은 발견입니다. 그걸로 가시죠.**

      제어 링크   USB-C 직결   192.168.55.100 ↔ 192.168.55.1   1.16ms / 편차 0.07ms
      인터넷      핫스팟
      원격        Tailscale

  조달이 필요 없다는 점, 주소가 고정된다는 점, AP isolation 과 무관해진다는 점
  전부 맞습니다. Wi-Fi 전력절약이 원인이었다는 규명도 감사합니다 —
  "40분 만에 조용히 사라진다"의 정체가 그거였군요.

  ★ 저희 쪽 확인 사항 하나. **Quest 는 Wi-Fi 로 Mac 에 붙습니다.**
    Mac 이 USB 이더넷(젯슨)과 Wi-Fi(Quest)를 동시에 쓰게 됩니다.
    저희 서버는 0.0.0.0 에 바인드하고 인증서 SAN 에 사설 IPv4 를 전부 넣으므로
    문제없을 것으로 봅니다. 실제로 붙여보고 이상하면 알려드리겠습니다.

  비컨은 **코드를 지우지 않고 남겨둡니다.** `JetsonBackend(host="192.168.55.1")`
  로 주소를 주면 비컨 없이 돌고, `host=None` 이면 비컨으로 찾습니다.
  나중에 무선으로 옮길 일이 생기면 그대로 쓸 수 있습니다. 젯슨 쪽에서는
  **비컨을 안 만드셔도 됩니다.**

  ※ 네이티브 CAN(mttcan)이 이미 올라와 있다는 것 좋은 소식입니다.
    트랜시버 조달이 되면 socketcan 쪽이 지연·지터에 유리하다는 판단에 동의합니다.
    저희 쪽은 어느 쪽이든 영향 없습니다.


================================================================================
 5. §8-E joint3 기구 고정 — 꼭 해주세요. 이유가 하나 더 있습니다
================================================================================

  말씀하신 두 가지(관성이 계속 변함 / 화면과 실물이 다름) 전부 맞습니다.
  거기에 **더 중요한 이유가 하나 있습니다.**

  ★ **손목 카메라가 joint3 끝에 붙습니다.**

    사용자 쪽 카메라 구성이 확정됐습니다 — 본체 후상방 1대 + **손목 1대**.
    손목 카메라는 모방학습에서 파지 정렬을 담당하는 핵심 입력입니다.

    joint3 이 무동력으로 자유롭게 돌면 **손목 카메라가 매번 다른 방향을
    보게 됩니다.** 같은 장면인데 이미지가 회전해서 들어오면 정책이 배우질
    못합니다. 데이터 수집 자체가 무의미해집니다.

    → 3번째 모터를 다는 것이 최선이고, 그 전까지는 **반드시 기구적으로
      고정**해 주세요. 핀이든 클램프든 접착이든 상관없습니다.
      고정된 각도만 알려주시면 저희가 URDF 에 반영하겠습니다.

  ※ 참고로 joint3 은 위치에 기여가 0 이라(랭크 2), 고정해도 **손끝이 갈 수
    있는 범위는 전혀 줄지 않습니다.** 손목 롤만 없어집니다.
    지금 단계에서는 잃는 게 없습니다.

 7. ★ 사용자 쪽 우선순위가 바뀌었습니다
================================================================================

  **학습은 급하지 않습니다. VR 로 실물을 구동하는 것이 먼저입니다.**

  즉 지금 중요한 것은 §11 시운전 계획의 **2~8단계를 끝까지 한 번 관통**하는
  것입니다. 데이터 수집·학습은 그 뒤입니다.

      2단계  CAN 피드백 확인          ← 하드웨어 연결 대기
      3단계  모터 파라미터 대조
      4단계  영점·부호 캘리브레이션   (joint1, joint2)
      5단계  기어비 교차검증
      6단계  단일 관절 구동  scale 0.1
      7단계  2관절 동시      0.1 → 0.3
      8단계  VR 연동 전체    ← ★ 여기가 목표

  저희 쪽은 8단계까지 필요한 것이 다 준비돼 있습니다. 젯슨에 하드웨어가
  붙는 시점에 바로 이어붙일 수 있습니다.

  참고로 학습 쪽 계획도 정해지긴 했습니다 (급하지 않음).
