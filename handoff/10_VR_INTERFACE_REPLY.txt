 0. 먼저 — B-2 에 프레임 혼선이 있습니다 (읽고 넘어가지 마세요)
--------------------------------------------------------------------------------
  B-2 의 축 이름은 hand_base 프레임 기준인데, B-3 은 EE 프레임을 hand_mount
  로 쓰라고 합니다. 두 프레임은 90°,-90°,0° 만큼 돌아가 있어서 축 이름이
  서로 다릅니다. 문서만 보고 구현하면 엉뚱한 축을 뺄 수 있습니다.

      hand_base w_x  (손바닥 법선축)  ==  hand_mount w_z
      hand_base w_y  (손가락 벌림축)  ==  hand_mount w_x
      hand_base w_z  (손목 롤)        ==  hand_mount w_y   ★ 절대 금지

  실측으로 확인했습니다 (임의 자세 400개):

      hand_base 에서 w_x 제거   조건수 중앙 53.1  90% 908.7
      hand_mount 에서 w_z 제거  조건수 중앙 53.1  90% 908.7   → 완전히 동일

  두 표현이 직교변환으로만 다르므로 특이값이 같습니다. 즉 물리적으로 같은 축을
  가리키는 게 맞고, 결론도 맞습니다. 다만 **문서에 프레임을 명시**해 주세요.

  Isaac Sim 담당께: B-3 대로 hand_mount 를 EE 로 쓰신다면,
  빼야 할 축은 **w_z (hand_mount 기준)** 이고 **w_y 를 빼면 절대 안 됩니다.**


 1. B-1 / B-2 독립 검증 결과
--------------------------------------------------------------------------------
  저희도 pinocchio 로 따로 재봤습니다. 보내주신 수치를 참조하지 않고 계산한 뒤
  대조했습니다.

  [B-1] 임의 자세 500개
      6D 자코비안 랭크   500개 전부 5      문서 주장 "전부 5"        O
      위치 3행 랭크      500개 전부 3      문서 주장 3               O
      자세 3행 랭크      500개 전부 3      문서 주장 3               O
      -> 태스크 6개 중 1개를 포기해야 한다는 결론 확인.

  [B-2] 임의 자세 400개, hand_base 프레임 기준 (문서와 같은 프레임)

      포기할 축              저희 중앙/90%          문서 중앙/90%      판정
      ---------------------------------------------------------------------
      손바닥 법선축 w_x       53.1 /    908.7       21.9 /    318     동급
      손가락 벌림축 w_y       60.2 /    903.6       26.6 /    731     동급
      손목 롤      w_z    4.8e10 / 3.0e11        2.5e10 / 1.7e11    발산

      -> **결론 완전히 일치합니다.** 손목 롤을 빼면 1e10 대로 발산하고,
         나머지 둘은 수십~수백대로 비슷합니다. 권장 구성도 동의합니다.

  ※ 안전한 두 축의 절대값이 2배쯤 차이 나는데, 이건 어느 쪽이 틀린 게 아닙니다.
    위치행(m/rad)과 회전행(무차원)이 섞인 자코비안의 조건수는 **길이 단위에
    따라 달라집니다.** 저희 쪽 실측:

        위치행을 m  로 두면   중앙    53.1
        위치행을 cm 로 두면   중앙   289.2
        위치행을 mm 로 두면   중앙  2888.3

    그러니 이 표는 절대값이 아니라 **순위**로 쓰셔야 합니다. 순위는 양쪽이 같고
    "손목 롤만 압도적으로 나쁘다"는 결론은 단위와 무관하게 유지됩니다.
    문서에 단위를 같이 적어주시면 다음부터 대조가 쉬워집니다.

  ※ 저희가 처음 잰 값이 문서와 축이 달라 보였는데, 원인은 저희가 hand_mount
    기준으로 쟀기 때문이었습니다. 위 §0 이 그 정리입니다.

 A. VR 담당이 채우는 항목
================================================================================

 A-1. VR 런타임과 장비 [확정]
--------------------------------------------------------------------------------
   헤드셋      Meta Quest 2
   런타임      **WebXR** (브라우저). OpenXR/SteamVR/Quest SDK 아닙니다.
               세션 모드 immersive-ar (실패 시 immersive-vr 로 폴백)
               레퍼런스 스페이스 local-floor
   좌표계      WebXR = RUB, y-up   (x=오른쪽, y=위, z=사용자 뒤쪽)
               로봇   = z-up

   변환 행렬 (확정, src/rpo_teleop/transforms.py):

       R_WEBXR_TO_ROBOT = [[ 0,  0, -1],
                           [-1,  0,  0],
                           [ 0,  1,  0]]

       즉  robot_x = -webxr_z    (앞)
           robot_y = -webxr_x    (왼쪽)
           robot_z = +webxr_y    (위)

   추가 보정   팔을 놓은 방향에 맞추는 수직축 yaw 보정을 곱합니다 (0/90/180/270).
               런타임에 VR 안에서 바꿀 수 있고, 아직 값이 확정되지 않았습니다.

               frame_mapping = yaw_rotation(base_yaw) @ R_WEBXR_TO_ROBOT

   ★ 미러(좌우 반사)는 쓰지 않습니다. det=-1 이라 회전이 아니고, 오른손
     로봇 손이 화면에 왼손으로 보입니다. Isaac 쪽에서도 넣지 마세요.

 A-2. 손 포즈 데이터 형식 [확정]
--------------------------------------------------------------------------------
   위치 단위   **m**
   자세 표현   **쿼터니언 (x, y, z, w)** — WebXR XRRigidTransform.orientation 원본
               오일러 아님. 순서는 xyzw.
   기준 원점   **local-floor** — 플레이 영역 바닥. 헤드셋 기준 아닙니다.
   무엇의 포즈  **컨트롤러 gripSpace** (targetRaySpace 도 같이 보내지만 미사용)
               gripSpace 는 "도구를 쥔 손" 기준이라 로봇 EE 자세에 자연스럽습니다.

   실제 전송 페이로드 (WebSocket, JSON):

       { type: "pose", data: {
           right: { grip:      { position:{x,y,z}, orientation:{x,y,z,w} },
                    targetRay: { position:{...},   orientation:{...} },
                    trigger: 0~1, squeeze: 0~1, stick:[x,y],
                    buttons: {...}, hand: false },
           left:  { ... },
           head:  { position:{...}, orientation:{...} } } }

   ★ 주의 — Quest 는 손 트래킹 중에도 같은 handedness 로 **합성 gamepad**
     (버튼 10개 / 축 0개)를 가진 oculus-hand 입력소스를 하나 더 보냅니다.
     이걸 컨트롤러와 구분하지 않으면 컨트롤러 슬롯을 덮어써서 포즈가 튑니다.
     저희는 src.hand 유무로 갈라서 처리합니다. Isaac 쪽에서 WebXR 을 직접
     받으실 일이 있으면 같은 처리가 필요합니다.
     (실측: 구분 전 각도 히스토그램이 48°/136° 로 이봉분포였고, 구분 후
      48.15° ± 0.00° 로 안정)

 A-3. 손가락 추적 데이터 형식 [현재 미사용 — 아래 참고]
--------------------------------------------------------------------------------
   현재 구현   손가락 추적을 **쓰지 않습니다.**
               오른손 **트리거 아날로그 값 하나(0~1)** 로 쥠 정도를 만듭니다.

                   trigger 0~1  →  grasp_to_servo(t)  →  서보각 8개 (rad)

   ★ 지적하신 "관절각이 아니라 서보각으로 가야 한다" — **이미 그렇게 하고
     있습니다.** servo_map/ 의 모듈을 그대로 씁니다.
     서보 공간에서 선형보간하고, 관절 공간 보간은 쓰지 않습니다
     (관절 공간으로 보간하면 중간에서 최대 11.44° 어긋나는 것을 실측 확인).

         SERVO_OPEN_DEG  = [-35, 35, -35, 35, -35, 35, -35, 35]
         SERVO_CLOSE_DEG = [ 90,-90,  90,-90,  90,-90,  90,-90]

   손 트래킹    Quest 손 트래킹 자체는 수신되고 있습니다 (위 A-2 의 oculus-hand).
                다만 손가락 관절까지 리타게팅하는 것은 아직 안 했습니다.
                우선순위상 뒤로 미뤄둔 항목입니다.
                필요해지면 그때 규격을 확정해서 다시 알려드리겠습니다.

   -> **지금은 5손가락→8서보 리타게팅을 만들지 않으셔도 됩니다.**
      액션은 서보각 8개 그대로 유지하시면 되고, 그 8개를 만드는 입력이
      트리거 하나일 뿐입니다.

 A-4. 제어 주기 [확정]
--------------------------------------------------------------------------------
   VR → 서버   **90 Hz** (Quest 2 디스플레이 주사율, requestAnimationFrame 기준)
   IK/제어 루프 **30 Hz**  (config 의 control_dt = 1/30)
   서버 → 화면  15 Hz (상태 브로드캐스트. 90Hz 를 그대로 밀면 헤드셋
                브라우저가 렌더링 시간을 뺏깁니다)

   ★ IK 속도 제한을 걸 때 주의점 하나 (저희가 겪은 버그):
     QP 솔버를 한 프레임에 N 번 돌리면 프레임당 이동량이 **정확히 N 배**가
     됩니다. 솔버는 solve() 한 번을 한 타임스텝으로 보기 때문입니다.
     실측: iters=5 에서 허용 7.20°/프레임 대비 36.00° (5.0배).
     dt 를 iters 로 나눠야 맞습니다. Isaac 쪽에서도 decimation 을 쓰신다면
     같은 함정이 있습니다.

 A-5. 작업공간 매핑 방식 [확정]
--------------------------------------------------------------------------------
   방식        **상대 변위 + 클러치**. 절대 위치 아닙니다.
               grip 을 누른 순간의 손 포즈를 기준으로 latch 하고, 그 뒤의
               변위만 전달합니다. 떼면 그 자리에 정지, 다시 잡으면 이어서.
               (마우스를 들었다 놓는 것과 같은 개념)

   스케일      1:1 아닙니다. 리치 비율로 자동 산출합니다.

                   scale = max_reach / human_reach     (human_reach = 0.65 m)

               전체 5-DOF 팔 : max_reach 0.459 m → **scale 0.706**
               임시 3-DOF 팔 : max_reach 0.253 m → **scale 0.390**

               URDF 가 바뀌면 자동으로 다시 계산됩니다. 고정 상수 아닙니다.

   회전        위치와 달리 스케일 없이 1:1 입니다.
               ★ 상대 회전을 **월드 기준**으로 만듭니다: R_rel = R_now · R_ref⁻¹
                 이걸 왼쪽에서 곱합니다: R_target = R_rel · R_home
                 (몸체 기준 R_home · R_rel 로 곱하면 축이 170.4° 어긋납니다.
                  저희가 실제로 겪은 버그입니다. 규약을 맞춰주세요.)

   도달 한계   목표를 [min_reach, max_reach] 구간으로 클램프하고, 클램프가
               걸리면 클러치 기준점을 재앵커해서 데드존이 생기지 않게 합니다.
               LeRobot 의 EEBoundsAndSafety 와 같은 역할입니다.

 A-6. 기록 형식 [계획]
--------------------------------------------------------------------------------
   **LeRobot dataset v3** 로 갈 계획입니다 (lerobot-record → lerobot-train ACT).
   자체 형식이나 HDF5 는 쓰지 않습니다.

   B-4 에서 요청하신 항목은 전부 남기겠습니다. 특히 **IK 잔차**는 지적하신
   이유 그대로 필요하다고 봅니다. 아래 §B-4 회신 참고.

 A-7. 햅틱/피드백 [현재 계획 없음]
--------------------------------------------------------------------------------
   진동 피드백 **쓰지 않습니다.** 접촉력을 시뮬에서 뽑아 넘기실 필요 없습니다.
   Isaac 쪽 설정을 늘리지 마세요.
   나중에 넣게 되면 그때 다시 말씀드리겠습니다.

 B. Isaac Sim 담당 항목에 대한 VR 쪽 회신

 B-1, B-2   위 §1 참조. 독립 검증했고 결론 동의합니다.
            프레임 표기만 §0 대로 정리해 주세요.

 B-3  EE 프레임 hand_mount — 동의합니다. 저희도 hand_mount 를 씁니다.
      Merge Fixed Joints 끄는 것도 확인했습니다.

 B-4  기록 항목 — 동의합니다. 저희 쪽에서 이미 다 갖고 있는 값들입니다.
        팔 관절각          IK 가 낸 q (실행값)
        EE 목표 포즈       클러치가 만든 target
        EE 달성 포즈       IK 후 FK
        손 서보각 8개      grasp_to_servo(trigger)
        IK 잔차            target - 달성  (위치/자세 따로)
      추가로 저희는 클램프 발생 여부와 클러치 engaged 여부도 남길 생각입니다.
      "왜 안 따라갔는지" 를 구분하려면 자유도 부족인지 도달 한계인지
      나눠야 하기 때문입니다.

 B-5  특이점 근처 안전 처리 — 동의하고, 저희 쪽 구현을 공유합니다.
      placo(QP)로 위치 soft 10000 : 자세 soft 1 로 풀고 있습니다.
      위치를 hard constraint 로 걸면 도달 불가 목표에서 QP 가 불능이 되어
      예외로 떨어집니다. soft 10000 은 정확도가 사실상 같으면서
      (연속 추종 p95 0.09 mm) 도달 불가 목표에서도 "갈 수 있는 가장 가까운
      자세"로 수렴합니다.
      여기에 관절 속도 제한을 켜고 목표 클램프를 겁니다.
      감쇠계수를 최소특이값에 따라 조절하라는 제안은 타당해 보입니다.

 B-6  손 서보각 액션 유지 — 동의합니다. 바꾸지 마세요. A-3 참고.

 B-7  나머지 그대로 — 확인했습니다.

 C. 못 준 항목에 대하여
================================================================================

 C-1  armature   VR 이 가감속이 급하다는 지적 동의합니다.
                 다만 저희 쪽 IK 는 관절 속도 제한을 URDF velocity(3.77 rad/s)
                 로 걸고 있어서, 지령 자체가 급격하지는 않습니다.
                 급한 것은 사람 손이지 지령이 아닙니다. 우선순위를 조금
                 낮게 보셔도 될 것 같습니다.

 C-2  마찰계수   파지를 하려면 필요하다는 것 동의합니다. 기다리겠습니다.

 C-3  damping/friction   기다리겠습니다.

 C-4  임시 팔 확정본  ★ **결정했습니다. 3-DOF 안(A) 으로 갑니다.**

      "위치 자유도가 2 라서 VR 위치 추종 테스트에 못 쓴다"는 지적은 맞습니다.
      저희도 독립 측정으로 확인했습니다:

          joint3 ±178° 전 범위 → 손끝 이동 0.000000 mm
          위치 자코비안 랭크 600개 전부 2
          방향별 전달률: 껍질 따라 95% / 안팎으로 1%

      그걸 알고 A 를 선택합니다. 이 임시 팔의 목적이 '위치 추종 성능'이 아니라
      **'파이프라인 검증'** 이기 때문입니다. 아래는 랭크와 무관하게 전부 돌아
      갑니다:

          Quest 입력 수신 → 좌표변환 → 클러치 → IK → 관절지령
          → 안전계층 → 3D 시각화 → 데이터 기록 → LeRobot 포맷

      위치 추종 성능 검증은 실물 5-DOF 팔로 하겠습니다.

      -> **추가로 만들어 주실 것 없습니다.** 이미 받은 robot_arm_temp/ 를
         그대로 씁니다. B 안(브래킷 신규)은 제작하지 마세요.
         C 안(4-DOF, temp4)은 폴더만 보관하고 지금은 쓰지 않습니다.

      저희 쪽에서는 위치 랭크가 3 미만이면 시작 화면과 대시보드에 경고를
      띄우도록 했습니다. 안팎으로 밀어도 안 움직이는 것을 고장으로 오해하지
      않게 하기 위해서입니다.


================================================================================
 D. 저희가 추가로 알려드릴 것 (요청에 없던 항목)
================================================================================

 D-1  IK 솔버를 반복 호출할 때 속도 제한이 무력화됩니다
      A-4 에 적었습니다. Isaac 쪽에서 decimation 을 쓰시면 같은 함정입니다.
      실측 5.0배. 저희는 dt 를 반복 횟수로 나눠서 해결했습니다.

 D-2  관절 한계가 정확히 ±180° 인 팔은 속도 제한을 반드시 켜야 합니다
      안 켜면 솔버가 +179°↔-179° 를 자유롭게 오갑니다. 기구학적으로는 같은
      자세라 QP 는 만족하지만 실물 모터에는 한 프레임에 360° 명령이 나갑니다.
      실측: 제한 없으면 한 스텝 최대 360.0°, 추종 p95 311 mm
            제한 켜면 2.5°, p95 44.8 mm

 D-3  홈 자세를 0 으로 두면 안 됩니다

      Isaac 쪽 초기 자세도 0 으로 두지 마세요.
