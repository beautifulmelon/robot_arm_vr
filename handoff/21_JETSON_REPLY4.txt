 2-1. link 필드가 문서에 없는 "trip" 을 내보내고 있었습니다  [§7-C]
--------------------------------------------------------------------------------
  ★ **그쪽이 맞습니다. 그리고 제 구현이 제 문서를 어기고 있었습니다.**

  실측했습니다.

      관측된 link 값 : ['lost', 'ok', 'stale', 'trip']
      문서 정의      : ['ok', 'stale', 'lost']
      → 문서에 없는 값을 내보냄

  `jetson_sim.py` 가 `link_stage()` 의 네 값을 그대로 흘려보내고 있었습니다.
  그쪽처럼 세 값만 처리하도록 구현하면 trip 구간이 조용히 미분류로 떨어집니다.

  ★ 게다가 그쪽 판단이 **개념적으로도 맞습니다.**
    trip 은 **모터 상태**이지 링크 상태가 아닙니다. 링크 필드에 넣는 건 범주
    오류이고, 워치독 트립 구간의 링크 상태는 실제로 "lost" 가 정확합니다
    (그만큼 지령이 안 온 것이니까요). TRIP 여부는 state 로 이미 드러나므로
    정보 손실도 없습니다.

  조치
      · 구현을 고쳤습니다: `link = "lost" if stage == "trip" else stage`
      · 문서에 "trip 을 넣지 말 것" 을 명시했습니다
      · 회귀 테스트를 붙였습니다 (`test_link_field_never_reports_trip`)
        ok→stale→lost→trip 구간을 1.2초 훑으며 관측된 값이
        {ok, stale, lost} 안에 드는지 봅니다

  → **그쪽 구현을 바꾸지 마세요. 저희가 맞췄습니다.**

 2-2. 비컨 테스트가 원래 취약했습니다  [§6]
--------------------------------------------------------------------------------
  지적하신 그대로입니다. `be.address is None` 을 connect() 직후에 단언하는데,
  그 찰나에 비컨이 도착하면 깨집니다. 저희도 예전에 한 번 겪고 "비컨을 빨리
  보내고 타임아웃을 늘리는" 식으로 덮었는데, **그건 증상만 미룬 것**이었습니다.
  원인 진단은 그쪽이 정확했습니다.

  조치 — 타이밍을 조정하는 대신 **순서를 고정**했습니다.

      (전) 젯슨 start() → 백엔드 connect() → address is None 단언   ← 경쟁
      (후) 백엔드 connect() → address is None 단언 → 젯슨 start()   ← 경쟁 없음

  젯슨이 아직 안 떴으니 비컨이 존재할 수 없습니다. 소켓을 비우는 방법보다
  확실합니다.

 2-3. ★ 저희가 추가로 찾은 것 — 테스트 포트가 고정이라 두 실행이 부딪힙니다
--------------------------------------------------------------------------------
  참조 구현을 그쪽 저장소에도 두셨으니 **그쪽도 겪습니다.** 알려드립니다.

  증상
      저장소 테스트와 전달 묶음 테스트를 **동시에(또는 연달아) 돌리면**
      무더기 에러가 납니다.

          본 저장소: 1 failed, 22 passed, 6 errors
          묶음     : 1 failed, 22 passed, 6 errors
          OSError: [Errno 48] Address already in use

  원인
      `test_jetson_link.py` 가 `BASE = 15005` 부터 고정 번호를 씁니다.
      같은 파일이 두 곳에 있으니 두 pytest 가 같은 포트를 잡습니다.

  ★ 여기서 저희가 한 번 더 틀렸습니다. 처음에 PID 로 대역을 나눴는데
    (`BASE = 20000 + (pid % 300) * 30`), **칸 수를 잘못 셌습니다.**
    프로세스당 30칸을 줬는데 테스트 29개가 각각 10칸씩 써서 290칸이 필요합니다.
    옆 프로세스 대역을 침범해서 증상이 그대로 남았습니다.

  최종 조치 — 칸을 세는 대신 **OS 에게 빈 포트를 받습니다.**

      def free_ports(n=3):
          socks, out = [], []
          for _ in range(n):
              s = socket.socket(AF_INET, SOCK_DGRAM); s.bind(("", 0))
              socks.append(s); out.append(s.getsockname()[1])
          for s in socks: s.close()      # 다 받은 뒤에 닫는다
          return out

  검증 — 저장소와 묶음을 **동시에** 3회 돌렸습니다.

      102 passed / 45 passed
      102 passed / 45 passed
      102 passed / 45 passed        전부 깨끗

  → 갱신본을 동봉합니다. 그쪽 저장소의 사본도 바꿔주세요.

 7. ★ 아직 한 번도 안 물어본 것 — 카메라 영상 경로
================================================================================

  지난 문서들을 다시 훑어보니 **카메라 영상을 어떻게 주고받을지 한 번도
  묻지 않았습니다.** 저희 쪽 누락입니다. 하드웨어가 붙기 전에 정해야 합니다.

  상황
    · 카메라 구성이 확정됐습니다 — **본체 후상방 1대 + 손목 1대**
    · 둘 다 **젯슨에 붙습니다** (`/dev/video*`)
    · 모방학습 데이터셋은 **관절각과 영상을 같은 타임스탬프로** 묶어야 합니다
    · 30 Hz UDP 제어 링크에 영상을 실을 수는 없습니다 — 별도 경로가 필요합니다

  선택지 (저희가 보기에)

    (A) **젯슨에서 직접 기록**
        영상이 네트워크를 안 건넙니다. 대역폭·지연 걱정이 없습니다.
        대신 관절각(Mac 이 앎)과 영상(젯슨이 앎)을 **나중에 맞춰야** 합니다.
        타임스탬프 동기가 관건입니다.

    (B) **젯슨 → Mac 스트림** (MJPEG/RTSP 등), Mac 이 전부 기록
        기록이 한 곳에 모여 동기가 쉽습니다.
        대신 링크가 영상을 감당해야 합니다. USB 직결이면 여유롭고,
        핫스팟이면 영상 때문에 제어 패킷이 밀릴 수 있습니다.

    (C) **양쪽 기록 + 사후 병합**
        가장 안전하지만 도구를 하나 더 만들어야 합니다.

  ★ 그쪽이 **이미 카메라 2대로 LeRobot 기록을 해보신 적이 있습니다**
    (12번 문서 §1-Q1 의 기존 Vuer 파이프라인). 그때 어떻게 하셨는지가
    가장 값진 정보입니다. 저희가 처음부터 고민할 필요가 없습니다.

  여쭙고 싶은 것

      1. 기존 파이프라인에서 영상과 관절각을 **어떻게 묶으셨나요?**
         (젯슨에서 통합 기록? 아니면 어딘가로 보내서?)
      2. 타임스탬프 동기를 어떻게 맞추셨나요?
      3. 해상도·프레임레이트는 얼마로 하셨나요?
      4. 그 방식에서 겪은 문제가 있었나요? (프레임 드롭, 동기 어긋남 등)
