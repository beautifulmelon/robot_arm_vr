 1-1. 결과
--------------------------------------------------------------------------------
  구성

      Mac 10.71.87.59  ──UDP 5005 지령──>  Jetson 10.71.87.203
                       <──UDP 5006 상태──   (우리 브리지 + SimBackend)

  맥 쪽은 `rpo_teleop.jetson_link.JetsonBackend` 를 **그대로** 썼습니다.
  젯슨 쪽은 우리 브리지입니다. 양쪽 다 실물 코드입니다.

      [1] 상태 패킷 수신
        PASS 젯슨이 상태 패킷을 보낸다
        PASS 배열 길이가 프로토콜과 맞는다        q=3개
        PASS link 필드가 온다                     link=ok

      [2] 왕복 지연 — 지령이 상태 패킷에 반영될 때까지
            n=108  평균 24.96ms  최대 46.49ms  편차 9.96ms
        PASS 최대 왕복이 2.5프레임(83ms) 이내     46.5ms

      [3] 상태머신
        PASS HOLD 지령에 여자되어 HOLD 로 올라간다
        PASS RUN 지령에 RUN 으로 간다
        PASS 지령한 0.05 rad 를 따라온다          0.0338 rad 이동
        PASS 소프트스타트가 완료됐다              soft_start=1.0

      [4] 워치독 (지령을 일부러 끊는다)
        PASS link 가 stale 로 바뀐다              rx_age=220ms
        PASS lost 에서 RUN 하차 + 재무장 요구
             state=HOLD link=lost rearm=True rx_age=722ms

      [5] 재무장
        PASS HOLD 로 관문이 열린다                rearm=False
        PASS RUN 으로 복귀한다                    state=RUN

      [6] TRIP 과 사람에 의한 해제
        PASS 지령이 완전히 끊기면 TRIP
        PASS RUN 지령만으로는 안 풀린다
        PASS HOLD + clear_trip 으로 해제되어 IDLE

      [7] 소자
        PASS DISABLED 지령에 IDLE 을 유지한다

      16 / 16 통과   LINK CHECK PASSED

  ※ 왕복 지연 46.5ms 는 링크 지연이 아닙니다. 핑은 편도 8.9ms 입니다.
    30 Hz 루프라 **제어 틱 + 송신 틱에서 최대 2프레임(66ms)이 원래 붙습니다.**
    실측 최대 46.5ms 는 그 안에 잘 들어옵니다. 정상입니다.

 1-2. ★ 연결을 막고 있던 것 — 젯슨의 ufw 방화벽
--------------------------------------------------------------------------------
  처음에는 상태 패킷이 한 장도 안 왔습니다. 원인을 좁힌 과정을 남깁니다.
  **맥 쪽에도 방화벽이 켜져 있으면 똑같이 겪게 됩니다.**

  관측

      맥 → 젯슨  UDP 5005       도착 안 함
      맥 → 젯슨  UDP 45999      도착 안 함     (포트 문제가 아님)
      맥 → 젯슨  TCP 22 (SSH)   정상
      맥 → 젯슨  ICMP           정상
      젯슨 → 맥  UDP 45998      **도착함**     ★ 비대칭
      젯슨 → 젯슨 루프백 5005    **도착함**     ★ 브리지는 정상

  브리지 종료 통계도 같은 그림이었습니다.

      STOPPED {'rx': 1, 'malformed': 0, 'tx': 3835, 'trips': 1, ...}

  · rx=1 — 4분 동안 받은 건 루프백으로 쏜 딱 한 장
  · malformed=0 — "도착했는데 파싱 실패"가 아니라 **아예 안 온 것**
  · tx=3835 — 나가는 길은 멀쩡

  ★ 비대칭이 결정적입니다. 핫스팟이 클라이언트 간 통신을 막는 거라면 양방향이
    죽습니다. 한 방향만 죽었다는 건 **수신 호스트의 방화벽**이라는 뜻입니다.

  실제 상태

      $ sudo ufw status verbose
      Status: active
      Default: deny (incoming), allow (outgoing), deny (routed)

      22/tcp     ALLOW IN  Anywhere
      8012/tcp   ALLOW IN  10.175.216.0/24    # Quest WebXR Vuer
      8765/tcp   ALLOW IN  10.175.216.0/24
      ... (전부 TCP. **UDP 규칙이 하나도 없음**)

  SSH 가 되는 건 22/tcp 허용 규칙이 있어서고, 핑이 되는 건 ufw 의 before.rules 가
  ICMP echo-request 를 통과시키기 때문입니다. 그 외 인바운드는 전부 차단 —
  관측된 그림과 정확히 일치합니다.

  조치

      sudo ufw allow proto udp from 10.71.87.0/24 to any port 5005:5007 \
           comment 'VR teleop bridge'

  이 한 줄 뒤에 16/16 이 통과했습니다.

  ★ 그쪽 확인 요청 두 가지
    (1) **맥 방화벽.** 저희 맥은 꺼져 있어서 문제가 없었지만, 켜져 있으면
        상태 패킷(5006)이 안 들어옵니다. 시스템 설정 → 네트워크 → 방화벽.
    (2) **USB 직결로 옮길 때 젯슨 쪽 규칙을 하나 더 넣어야 합니다.**

            sudo ufw allow proto udp from 192.168.55.0/24 to any port 5005:5007

    ※ §12-a 로 두 번 물으셨던 AP isolation 은 실제로 없었습니다. 다만 그것과
      무관하게 이 방화벽이 막고 있었습니다. 격리 확인만으로는 못 잡았을
      문제라, 실제로 붙여보길 잘했습니다.

 2. 결함 3건 — 저희 독립 프로브로 재검증
================================================================================

  그쪽 테스트가 아니라 **저희가 따로 만든 프로브**로 찔렀습니다. 참조 구현을
  직접 띄우고 원시 UDP 로 공격하는 방식입니다. 젯슨 실물(ARM64)에서 돌렸습니다.

      === 결함 1: 새 세션이 HOLD 로 안 내려감 ===
        세션1                state=RUN
        세션2 RUN 만 전송    state=HOLD  이동 0.010 rad   ✅ 수정됨
        HOLD 후 재무장       state=RUN                    ✅ 교착 없음

      === 결함 2: 링크 복구 시 재무장 없이 이어감 ===
        1.5초 두절 후        state=HOLD
        복구 직후            이동 0.000 rad               ✅ 수정됨
                             (수정 전 0.627 rad)

      === 결함 3: 보간 주기를 올려도 속도제한이 유지되는가 ===
        보간 없음            0.303 rad/s (한계 0.377)     ✅
        motor_hz=100         0.293 rad/s                  ✅
        motor_hz=500         0.291 rad/s                  ✅
                             (수정 전 500Hz 에서 5.100 rad/s = 13.5배)

  그리고 그쪽 테스트 38개를 젯슨에서 그대로 돌려 **38 passed** 확인했습니다.

  ★ 결함 3 의 수정 방식은 **그쪽 것이 저희 것보다 낫습니다.**
    저희는 `dt != 1/rate_hz` 면 기동을 거부하는 방식이었는데, 그쪽은 제어 루프를
    송신 루프에서 분리했습니다. 그러면 두 주기가 달라도 안전계층은 control_hz
    로만 돌아서 **문제가 애초에 성립하지 않습니다.** 저희 브리지도 그 구조로
    바꿨습니다.

  ★ `link` 필드를 새로 둔 것도 좋은 판단입니다. 저희는 "state 가 링크 끊김을
    안 알린다"고만 지적했는데, state 에 통신을 섞는 대신 **직교한 축을 만든
    것**이 더 깔끔합니다. 그대로 받았습니다.

 3. 질문 가~마 답변
================================================================================

 가. lost 임계 (stale 이 아니라 lost 에서 RUN 하차)
--------------------------------------------------------------------------------
    → **동의합니다.** 사실 저희도 회신을 받기 전에 독립적으로 `lost` 를
      기본값으로 구현해 두었습니다. 근거도 같았습니다 — stale(100ms)에서
      내리면 30 Hz 기준 3프레임 손실마다 클러치를 다시 잡아야 해서 조종이
      불가능해집니다.

      저희 구현은 `rearm_after` 설정으로 `stale`/`lost`/`never` 를 고를 수
      있고 기본값이 `lost` 입니다. 나중에 실링크 데이터를 보고 조정하기 쉽게
      열어둔 것이지 기본을 바꿀 생각은 없습니다.

 나. link / await_rearm 필드
--------------------------------------------------------------------------------
    → **반영 완료했고 실링크에서 동작을 확인했습니다** (§1-1 의 [4]).

          state=HOLD  link=lost  await_rearm=True  rx_age=722ms

      저희 쪽 매핑은 이렇습니다.

          link_stage()  ok / stale / lost / trip
          → 패킷 link   ok / stale / lost / **lost**   (trip 은 lost 로 합침)

      프로토콜에 link 는 ok|stale|lost 세 값만 정의돼 있어서, trip 구간은
      lost 로 보냅니다. TRIP 여부는 state 로 이미 드러나므로 정보 손실이
      없다고 봤습니다. 다르게 원하시면 알려주세요.

 4. 동봉 — SimBackend (스톨 + 중력 낙하)
================================================================================

  `rpo_jetson/backend.py` 의 `SimBackend` 입니다. VR 의 MockBackend 를 확장한
  것으로, 인터페이스는 `MotorBackend` 그대로라 갈아끼우기만 하면 됩니다.

      set_stall([True, True])      관절을 물리적으로 막는다. 지령이 와도 안 움직임
      sag_rate / sag_to            소자 상태에서 중력으로 처지는 속도와 도달점
      max_rate                     관절 최대 속도 포화 (실물에는 있는 것)
      set_temperature / set_errors 온도·에러코드 주입
      reads                        한 사이클에 몇 번 읽혔는지 (CAN 왕복 검증용)

  이걸로 **처음 검증 가능해진 것 두 가지**입니다.

    · **이격 제한(§5-5)** — 관절을 막고 지령을 계속 밀어넣어 오차가 쌓이는지
      본 뒤, 장애물을 치우는 순간 튀는 양을 잽니다. 1차 지연 목으로는 항상
      수렴해서 이 상황 자체를 만들 수 없었습니다.
    · **HOLD vs DISABLED** — 소자하면 실제로 처집니다. 낙하가 없으면 mode 를
      3단계로 나눈 이유가 화면에서 보이지 않습니다.

  저희 회귀 테스트에 다음이 들어 있습니다. 그대로 가져가셔도 됩니다.

      test_command_lag_bounded_against_real_stall
      test_disabled_backend_sags_under_gravity

 7. 저희가 되묻는 것
================================================================================

  A. **맥 쪽 방화벽이 켜져 있는지 확인해 주세요.** 켜져 있으면 상태 패킷
     (UDP 5006)이 안 들어옵니다. 저희가 §1-2 에서 겪은 것과 같은 증상입니다.

  B. USB 직결로 옮기는 시점을 정하죠. 저희는 언제든 가능합니다.
     그때 젯슨에 규칙을 하나 더 넣습니다 (192.168.55.0/24).
