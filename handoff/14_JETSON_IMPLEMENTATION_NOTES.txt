 2-①. 규격이 유효하지 않은 JSON 을 만들고 있었습니다
--------------------------------------------------------------------------------
  증상
      상태 패킷의 temp/q 배열에서 값이 없는 자리를 NaN 으로 채우고 있었습니다.
      **NaN 은 JSON 표준에 없습니다.**

          {"temp": [35.0, 36.0, NaN]}     ← 이건 JSON 이 아닙니다

      파이썬 json 은 관대해서 NaN 을 그냥 써버리고 읽을 때도 받아줍니다.
      그래서 파이썬끼리는 멀쩡히 돕니다. 그런데 엄격한 파서는 패킷을 통째로
      거부합니다. 저희는 **대시보드 /state 가 HTTP 500 으로 죽으면서** 발견했습니다
      (starlette 의 JSONResponse 가 allow_nan=False 로 직렬화합니다).

  왜 여러분에게도 문제인가
      · 3축 중 2축만 모터가 있으니 미장착 자리에 값이 없습니다 → NaN 이 나올 자리
      · 모터 피드백이 아직 안 온 시점의 온도/토크도 마찬가지
      · 나중에 파이썬이 아닌 도구(Isaac, 로깅, 다른 언어 클라이언트)가 붙으면
        그때 깨집니다. 그때는 원인을 찾기 훨씬 어렵습니다.

  조치 (양쪽 다 적용해 주세요)
      값이 없는 자리는 **null** 로 보냅니다. 직렬화할 때 allow_nan=False 를
      명시해서, NaN 이 섞이면 조용히 나가는 게 아니라 **그 자리에서 터지게** 합니다.

          json.dumps(payload, allow_nan=False)     # ★ 반드시

      동봉한 jetson_link.py 의 _nums() 가 그 처리입니다. 그대로 쓰셔도 됩니다.

          {"temp": [35.0, 36.0, null]}    ← 이렇게

  테스트: test_packets_are_strict_json_no_nan


 2-②. 워치독이 영원히 안 걸리는 구조였습니다
--------------------------------------------------------------------------------
  이게 셋 중 제일 위험합니다. **링크가 죽어도 로봇이 계속 명령을 받는 상태**가
  됩니다.

  증상
      SafetyLayer.clamp() 안에서 "마지막 명령 시각"을 갱신하고 있었습니다.
      원래는 clamp() 가 "명령이 올 때마다" 불린다는 전제였습니다.

      그런데 젯슨은 제어 주기(30~500 Hz)마다 clamp() 를 부릅니다. 링크가 끊겨도
      마지막 지령을 계속 흘려보내야 하니까요. 그러면 clamp() 가 매 틱 시계를
      리셋해서 **경과 시간이 절대 늘지 않습니다.**

          링크 끊김 → 지령 안 옴 → 그래도 제어 루프는 돌음
                   → clamp() 호출 → 시계 리셋 → 워치독 영원히 안 걸림

      저희 테스트에서 4초를 끊어도 트립이 안 나서 발견했습니다.

  근본 원인
      **"지령이 왔다"와 "제어 스텝을 돈다"는 다른 사건인데 같은 시계를 썼습니다.**

  조치
      시계를 둘로 나눕니다.

          note_command()   ← UDP 지령을 수신한 순간에만 호출. 워치독 기준.
          clamp()          ← 제어 주기마다 호출. 워치독과 무관.

      동봉한 motor_backend.py 에 반영돼 있습니다.

          def _accept(self, cmd):        # UDP 수신 시
              self.safety.note_command()  # ★ 여기서만

          def _tick(self):               # 제어 주기마다
              stage = self.safety.link_stage()   # ok / stale / lost / trip
              q = self.safety.clamp(target, actual)

      ★ 여러분이 C++ 이나 다른 구조로 가시더라도 이 분리는 반드시 필요합니다.
        "제어 루프가 도는 것"으로 워치독을 리셋하면 안 됩니다.

  테스트: test_watchdog_freezes_before_tripping


 2-③. 트립 해제가 패킷 손실에 조용히 사라졌습니다
--------------------------------------------------------------------------------
  증상
      §1-D 에서 "clear_trip 은 버튼을 누른 그 프레임에만 true, 그 뒤 즉시 false"
      로 합의했습니다. 자동 재시도를 막으려는 것이었고, 의도는 옳습니다.

      그런데 그 한 장짜리 패킷이 손실되면 **사람이 버튼을 눌러도 아무 일도
      안 일어납니다.** 화면도 아무 말을 안 해서 "눌렀는데 왜 안 되지"가 됩니다.
      손실률 30% 링크에서 실제로 재현됐습니다.

  조치 — 두 가지를 같이
      (a) **한 번의 누름을 1초 창(窓) 동안만 재전송**합니다.
          손실은 이기고, 창이 닫히면 멈추므로 자동 재시도는 되지 않습니다.
          트립이 풀리면 즉시 재전송을 멈춥니다.

              누름 → [1초 동안 매 프레임 clear_trip=true] → 창 닫힘 → 멈춤
              (그 사이 트립이 풀리면 바로 멈춤)

      (b) **화면이 정직해야 합니다.** 링크가 죽어 있으면 버튼을 잠그고
          "링크가 끊겨 있어 지금은 전달되지 않습니다" 라고 알립니다.
          통신이 완전히 두절된 동안은 어차피 전달이 불가능합니다.
          조용히 실패하면 사람은 눌렀다고 믿습니다.

      젯슨 쪽은 바뀔 게 없습니다. 같은 seq 로 여러 번 오는 게 아니라
      **매 프레임 새 seq 로 clear_trip=true 가 오는 것**이라 기존 수락 규칙
      (mode 가 HOLD/DISABLED 일 때만, RUN 이면 무시) 그대로면 됩니다.

  테스트: test_clear_trip_survives_packet_loss / test_clear_trip_window_expires

 3. 구현하면서 정해진 세부 규칙 (규격 보완)
================================================================================

  문서로만 있던 것을 코드로 옮기면서 애매했던 부분들입니다. 아래대로 맞춰주세요.

 3-1. HOLD 의 목표값 — 전이별로 다릅니다
--------------------------------------------------------------------------------
      DISABLED → HOLD   목표 := **현재 실제 q**   (처져 있는 데서 안 튀게)
      RUN      → HOLD   목표 := **마지막 수락 q** (뒤처진 위치를 굳히지 않게)
      워치독 freeze     목표 := **마지막 수락 q**

  RUN→HOLD 에서 "현재 실제 q" 를 쓰면, 모터가 지령보다 뒤처진 상태에서 그
  뒤처진 위치가 목표로 굳고, 다시 RUN 갈 때 원래 지령으로 튑니다.

 3-2. IDLE 과 HOLD 의 경계
--------------------------------------------------------------------------------
      IDLE   소자. 링크는 살아있음. 부팅 직후 / 트립 해제 직후.
      HOLD   여자. 토크로 자세 유지. q 추종은 안 함.

      IDLE 상태에서 mode=HOLD 지령이 오면 → **여자하고 HOLD 로 올라갑니다.**
      이건 정상입니다 (연결 절차 2)의 사전 점검 상태).
      여자하는 순간 지령을 현재 실제 위치로 리셋하고 소프트스타트를 겁니다.

      ★ IDLE 에서 RUN 으로는 한 번에 가지 않습니다. IDLE → HOLD → RUN.

 3-3. 트립 해제 후
--------------------------------------------------------------------------------
      clear_trip 수락 → **IDLE (소자)**. 바로 RUN 으로 가지 않습니다.
      Mac 쪽은 추가로, 트립 후에는 **사람이 클러치를 다시 잡아야** RUN 을
      내보내게 했습니다. 링크가 붙자마자 사람이 팔에서 손 뗀 사이에 움직이는
      것을 막습니다.

 3-4. 상태 패킷은 '지령 패킷의 송신지'로 되돌려 보냅니다
--------------------------------------------------------------------------------
      젯슨이 Mac 의 IP 를 알 필요가 없습니다. 핫스팟에서 Mac IP 가 바뀌어도
      자동으로 따라갑니다. 설정에 Mac 주소를 넣지 마세요.

 3-5. 비컨은 처음 몇 개를 빠르게
--------------------------------------------------------------------------------
      1 Hz 로만 보내면 Mac 이 젯슨을 찾는 데 최대 1초가 걸리고, 그 사이 지령이
      한 장도 안 나갑니다. 부팅·재접속 직후가 사람이 기다리는 구간입니다.

          처음 5개는 0.2초 간격 → 그 뒤 1초 간격

      비컨 본문의 ip 필드보다 **실제 UDP 송신지 주소를 우선**합니다.
      (다중 인터페이스에서 본문 IP 가 닿을 수 없는 주소일 수 있습니다)

 3-6. 이번 차수 배열 규칙 재확인
--------------------------------------------------------------------------------
      q 배열 길이는 **3 유지**. 젯슨은 q[0], q[1] 만 모터로 내보내고 q[2] 는 버림.
      상태의 q[2] 는 0.0, temp[2] 는 **null**, err[2] 는 0.
      손은 이번 차수에 안 씁니다 → Mac 은 grasp/servo 필드를 **아예 안 보냅니다.**

 7. 덧붙임
================================================================================

  버그 3건이 전부 **문서가 아니라 돌려보니까** 나왔습니다. 특히 ②는 규격서를
  아무리 정확히 읽어도 같은 함정에 빠집니다. 규격에 "워치독"이라고만 적혀 있고
  그 시계를 언제 리셋하는지는 안 적혀 있었기 때문입니다.

  그래서 실물 모터를 붙이기 전에 여러분 쪽에서도 **가짜 Mac** 을 하나 만들어
  두시길 권합니다. 저희 JetsonBackend 를 그대로 쓰셔도 됩니다 (jetson_link.py).
  양쪽이 각자 상대 없이 검증된 상태로 만나는 게 가장 빠릅니다.
