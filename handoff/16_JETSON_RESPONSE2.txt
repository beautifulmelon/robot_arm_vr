 1. §2 버그 3건 — 전부 동의합니다
================================================================================

  ①  유효하지 않은 JSON (NaN)
      저희가 못 본 것입니다. 정당합니다. `allow_nan=False` 로 그 자리에서
      터지게 하는 처리도 옳습니다. 특히 저희는 **미장착 joint3 자리**가 항상
      있으니 직격입니다. `_nums()` 그대로 쓰겠습니다.

  ②  워치독이 영원히 안 걸림
      ★ 저희도 독립적으로 같은 것을 찾았습니다.
        `SafetyLayer.clamp()` 안에서 `_last_update = now` 를 매번 갱신하니,
        "지령이 왔다"가 아니라 "clamp 가 불렸다"를 재고 있었습니다.

        여기에 자기모순이 있습니다. freeze 는 "지령이 끊겨도 계속 내보내는
        것"인데, 내보내려면 clamp 를 불러야 하고, 부르면 시계가 리셋됩니다.
        **freeze 를 구현하는 행위 자체가 워치독을 무력화합니다.**

        `note_command()` 분리로 정확히 해결됐습니다. 동의합니다.

  ③  트립 해제가 패킷 손실에 사라짐
      이것도 저희가 못 본 것입니다. "한 프레임만 true" 라는 저희 제안이
      손실 링크에서 조용히 실패한다는 것, 재현해서 찾아주셔서 감사합니다.
      1초 창 재전송 + 화면이 정직할 것, 둘 다 동의합니다.
      젯슨 쪽은 바뀔 게 없다는 판단도 맞습니다.

  ※ §7 의 "버그 3건이 전부 문서가 아니라 돌려보니까 나왔다"는 말씀,
    저희 쪽 결과가 그 말을 한 번 더 증명합니다. §2 를 보십시오.

 2. ★ 참조 구현에서 새로 찾은 결함 3건 (실측 로그 첨부)
================================================================================

  검증 방법: `jetson_sim.FakeJetson` 을 직접 띄우고 원시 UDP 로 지령을 쏴서
  상태 전이를 관찰했습니다. 맥(x86 아님, Apple Silicon)과 젯슨(ARM64) 양쪽에서
  같은 결과가 나왔습니다.


 2-1. 새 세션이 HOLD 로 안 내려갑니다 [심각]
--------------------------------------------------------------------------------
  jetson_sim.py 의 주석은 이렇습니다.

      # ★ 새 세션은 HOLD 로 받는다. Mac 이 재시작한 직후 팔이 갑자기
      #   움직이지 않게. RUN 은 Mac 이 다시 요청해야 한다.

  그런데 그 아래 모드 전이 코드로 **그대로 흘러내려갑니다.** 세션 변경 시
  state 를 HOLD 로 바꿔놓지만, 같은 패킷의 `mode` 가 RUN 이면 바로 아래에서
  다시 RUN 으로 올라갑니다.

  실측 (velocity_scale=1.0, 세션2의 첫 패킷부터 mode=RUN 만 전송)

      [맥]
        세션1 정상 추종      state=RUN
        세션2 첫패킷부터 RUN state=RUN  q=[0.675 0.175]
      [젯슨 ARM64]
        세션1 정상 추종      state=RUN
        세션2 첫패킷부터 RUN state=RUN  q=[0.524 0.057]
        -> 기대: HOLD / 실제: RUN  ❌ 재현됨

  ★ 테스트가 이걸 못 잡는 이유
    `test_new_session_resets_seq_and_drops_to_hold` 가 `be2.hold()` 를
    **먼저 부릅니다.** 즉 "예의 바른 Mac" 경로만 검증하고, "첫 패킷이 RUN 인
    Mac" 은 한 번도 안 돌려봤습니다.

  ★ 실제 위험 시나리오
    **사람이 클러치를 잡은 채로 Mac 프로세스가 죽었다 살아나는 경우.**
    재시작한 Mac 은 클러치가 눌려 있으니 곧바로 RUN 을 내보내고, 팔이 즉시
    움직입니다. 이 규칙을 넣은 목적 그 자체가 무산됩니다.

  조치 제안 (젯슨 쪽)
    세션이 바뀌면 `_await_rearm = True` 를 세우고, `mode` 가 HOLD 또는
    DISABLED 인 패킷을 **한 번 받기 전까지 RUN 을 거부**합니다.
    Mac 쪽은 바뀔 게 없습니다 (이미 hold() 를 먼저 보내고 계십니다).


 2-2. 링크가 복구되면 재무장 없이 그대로 이어갑니다 [심각]
--------------------------------------------------------------------------------
  13번 문서 §6-3 에서 이렇게 합의했습니다.

      100 ms 초과   HOLD 로 내려가 freeze
      ※ 링크가 복구되면 HOLD → RUN 은 자동으로 가지 마세요.
        Mac 이 mode="RUN" 을 다시 보내야 움직이게 해주세요.

  구현은 **끊긴 동안 RUN 에서 내려오지 않습니다.** 내부적으로
  `link_stage()` 는 `"lost"` 인데 대외 `state` 는 계속 `"RUN"` 입니다.

  실측 (freeze 0.1s / lost 0.5s / trip 3.0s, 1.5초 통신 두절 후 복구)

      [맥]
        1.5초 두절 후   state=RUN   stage=lost   rx_age=1.52s
        복구 직후       q [ 0.2 -0.1] -> [0.972  0.672]
      [젯슨 ARM64]
        1.5초 두절 후   state=RUN   stage=lost   rx_age=1.52s
        복구 직후       q [ 0.2 -0.1] -> [0.827  0.527]
        -> 재무장 요구 없이 0.627 rad (약 36°) 이동  ❌ 재현됨

  두 가지가 걸립니다.

    (a) **`state` 필드가 링크 끊김을 안 알립니다.**
        대시보드가 `state` 를 보고 있으면 링크가 죽은 1.5초 동안 "정상 추종
        중" 으로 표시됩니다. `rx_age_ms` 를 따로 보지 않으면 모릅니다.

    (b) **재무장 관문이 없습니다.**
        RUN 에서 안 내려오니 "다시 RUN 요청" 이라는 절차가 성립하지 않고
        그냥 이어집니다. 사람이 그사이 팔에서 손을 뗐어도 마찬가지입니다.

  ★ `test_watchdog_freezes_before_tripping` 이 freeze 구간에서
    `state == STATE_RUN` 을 **단언**하고 있습니다. 의도적 선택으로 보입니다.
    그렇다면 §6-3 문구를 고치든 구현을 고치든 **한쪽을 맞춰야 합니다.**
    저희는 구현을 §6-3 에 맞추는 쪽을 권합니다 — 27 N·m 팔이고, 링크가
    끊겼다는 사실이 대외 상태에 안 드러나는 건 위험합니다.

  조치 제안
    `stale` 진입 시 `state := HOLD` (토크 유지, 지령 동결).
    복구 후 Mac 이 `mode=RUN` 을 다시 보내야 RUN 으로 올라감.
    Mac 쪽은 이미 "트립 후엔 클러치를 다시 잡아야 RUN" 을 구현하셨으니
    (§3-3), 그 규칙을 링크 복구에도 그대로 적용하시면 됩니다.


 2-3. dt 와 rate_hz 가 어긋나면 속도 제한이 뚫립니다 [젯슨 직격]
--------------------------------------------------------------------------------
  `FakeJetson(dt=..., rate_hz=...)` 이 독립 인자인데 일관성 검사가 없습니다.
  `SafetyLayer.clamp()` 의 `max_step = velocity_limit * self.dt` 라서,
  틱을 빠르게 돌리면 **매 틱마다 dt 만큼의 이동을 허용**합니다.

  실측 (velocity_scale=0.1, URDF 3.77 rad/s → 한계 0.377 rad/s)

      [맥]
        rate_hz=  30  dt=1/30 -> 0.344 rad/s (한계 0.377)  ✅
        rate_hz= 500  dt=1/30 -> 4.689 rad/s              ❌ 12.4배
      [젯슨 ARM64]
        rate_hz=  30  dt=1/30 -> 0.374 rad/s (한계 0.377)  ✅
        rate_hz= 500  dt=1/30 -> 5.100 rad/s              ❌ 13.5배

  ★ 젯슨이 맥보다 더 크게 뚫렸습니다(12.4 → 13.5배). 틱이 더 촘촘히 돌아서
    그렇습니다. 즉 **빠른 기계일수록 더 위험해지는** 성질입니다.

  ★ 왜 저희에게 직격인가
    12번 문서 §1-Q6 에서 **"젯슨이 30 Hz 를 받아 500 Hz 로 보간"** 하기로
    합의했습니다. 그 계획을 이 코드에 그대로 얹으면 정확히 위 함정에
    빠집니다. 5.1 rad/s 는 URDF 속도 한계 3.77 rad/s 마저 넘습니다.

  조치 (젯슨 쪽에서 처리)
    구조를 이렇게 고정합니다.

        UDP 30Hz ─> SafetyLayer(dt=1/30) ─> 보간기 500Hz ─> CAN
                    여기서만 제한            안전계층 출력 사이만 메움

    보간을 안전계층 **뒤**에 두면 보간기가 한계를 넘을 수 없습니다.
    그리고 `assert abs(dt - 1/rate_hz) < 1e-6` 을 넣어 어긋나면 기동
    자체를 거부하게 합니다.

 4. §6 미결 질문 답변

 a. 핫스팟 UDP 양방향 소통 (AP isolation)      ★ 최우선
--------------------------------------------------------------------------------
    → **격리 없습니다. UDP 통합니다.**

    두 망에서 확인했습니다.
      · 캠퍼스 Wi-Fi(/21) : 핑 스윕으로 259대 상호 응답 확인 → 격리 없음
      · Android 핫스팟    : 맥↔젯슨 직접 통신 확인 → 격리 없음

    이번 방식은 성립합니다. **다만 §5 를 먼저 봐주세요. 더 나은 선택지가
    생겼습니다.**

 b. 비컨 방식 / 젯슨 호스트명
--------------------------------------------------------------------------------
    → 젯슨 호스트명은 **`ubuntu`** 입니다. (avahi 켜면 `ubuntu.local`)

    비컨 방식 자체는 동의합니다. 다만 **§5 의 USB 직결로 가면 주소가 고정돼서
    비컨이 통째로 불필요해집니다.** 핫스팟을 계속 쓰기로 하면 그때 구현
    하겠습니다. 3-5 의 "처음 5개는 0.2초 간격" 도 좋은 디테일입니다.

 c. 워치독 3단계 시간 (100ms / 표시 / 3초)
--------------------------------------------------------------------------------
    → **3단계 구조는 동의. 다만 TRIP 3초는 재검토를 제안합니다.**

    구조(freeze / lost / trip)는 2단계보다 확실히 낫습니다. 그건 유지하죠.

    그런데 3초라는 값의 근거가 "핫스팟은 0.5초 끊김이 일상적" 이었습니다.
    저희 실측에서 그 전제가 흔들립니다 (§5-2). **10분 3000패킷 중 100 ms 를
    넘은 게 0개**입니다. 원래 합의였던 100ms/500ms 로도 한 번도 안 걸렸을
    겁니다.

    3초가 부담스러운 이유: 그동안 팔이 마지막 지령을 향해 계속 갑니다.
    §2-2 의 재무장 부재와 겹치면 **최대 3초를 아무 확인 없이 움직이고, 복구
    후에도 그대로 이어갑니다.**

    제안: **TRIP 을 1.0초로.** freeze 100ms 는 그대로.
          그리고 §2-2 대로 stale 에서 `state := HOLD` 로 내려가면, 1초든
          3초든 팔은 이미 100ms 에 멈춰 있으므로 안전 여유가 훨씬 큽니다.
          값 자체는 설정으로 빼서 실제 링크로 30분 이상 돌려보고 확정하죠.

 d. 손 서보 매핑 확인 절차
--------------------------------------------------------------------------------
    → 동의합니다. **§5-1 의 지적이 맞습니다.** 저희 12번 문서 §5 의 결론은
      부호 교대 규약까지만 유효하고, 주기가 2 라 손가락 순서는 검증되지
      않았다는 것 — 정확합니다. 결론을 그 범위로 정정합니다.

    절차에 한 가지만 보태겠습니다. **한 서보만 30° 는 무리입니다.**
    손가락당 서보 2개가 평행 4절로 묶여 있어서 한쪽만 크게 돌리면 링크에
    부하가 걸립니다. **10~15° 로 시작**하시죠. 그 정도면 어느 손가락이
    움직였는지 눈으로 충분히 보입니다.

    ※ `SERVO_CLOSE_DEG` 가 정확히 ±90° 인데 `clamp_servo` 의 정격 한계도
      ±90° 입니다. **닫힘 자세가 리밋에 딱 걸쳐 마진이 0** 입니다.
      2차 때 88° 정도로 내리는 걸 제안합니다.

    ※ `hand_model.py` 가 참조하는 `assets/hand/hand.urdf` 가 패키지에
      없습니다. 2차 전에 같이 주세요.

 e. q 배열 3 유지 + q[2] 버리기
--------------------------------------------------------------------------------
    → **동의합니다.** 나중에 프로토콜을 안 바꿔도 된다는 근거가 타당합니다.
      상태의 q[2]=0.0, temp[2]=null, err[2]=0 그대로 하겠습니다.

    ★ 다만 물리적으로 짚을 게 있습니다. **joint3 은 무동력 회전 관절이고
      그 끝에 손 0.4 kg 이 매달려 있습니다.** 팔이 움직일 때마다 손목이
      자유롭게 돌아가서 (a) 관성이 계속 변하고 (b) 화면의 자세와 실물이
      다르게 보입니다.

      → **joint3 을 기구적으로 고정(핀/클램프)할 수 있는지** 확인 부탁드립니다.
        고정하는 쪽이 훨씬 깔끔하고, 시운전 관찰도 쉬워집니다.

 f. 시운전 중 손 서보 — 펴진 자세 고정 vs 소자
--------------------------------------------------------------------------------
    → **소자를 권합니다.**

    이유: 팔 시운전 중 손 서보 버스를 안 건드린다는 §4-(c) 와 일관됩니다.
    토크를 걸어두면 그 상태를 유지하려고 전류를 계속 먹고, 팔이 흔들릴 때
    서보가 버티다가 과부하가 날 수 있습니다. 소자하면 손가락이 늘어지지만
    무게중심은 이미 §4-(a) 로 반영돼 있어 달라지는 게 없습니다.

    다만 "덜렁거려서 관찰이 어렵다"는 우려에는, **소자 전에 한 번 펴진
    자세로 보내고 나서 소자**하면 됩니다. 자세는 유지되고 전류는 안 먹습니다.

 5. ★ 네트워크 — 조달 없이 유선급 링크를 확보했습니다

 5-1. USB-C 직결
--------------------------------------------------------------------------------
  Jetson 개발자 키트는 USB-C 로 호스트에 연결하면 L4T 가 가상 이더넷을
  자동으로 올립니다. **케이블 하나 외에 조달할 것이 없습니다.**
  "장비 조달보다 진행이 우선" 이라는 §6 판단과 충돌하지 않습니다.

      맥  192.168.55.100  ←──USB-C 케이블──→  젯슨  192.168.55.1

  실측 (40 패킷)

      손실 0.0%   min 1.008 / avg 1.164 / max 1.380 / stddev 0.069 ms

  · **고정 주소** → §6-2 비컨 구현이 통째로 불필요
  · **AP isolation 무관** → §12-a 확인 절차 불필요
  · Wi-Fi 는 그대로 두고 인터넷/SSH 용으로 병행 사용 (지금 그렇게 쓰고 있습니다)

 5-2. 핫스팟 — 원인을 찾았습니다
--------------------------------------------------------------------------------
  지난번 "40분 만에 100% 손실 + ARP 엔트리 소멸" 의 원인은 **Wi-Fi 전력절약**
  이었습니다. 리눅스 드라이버 기본값이 켜져 있어서 유휴 시 기기가 네트워크에서
  조용히 사라집니다.

      sudo nmcli connection modify "<SSID>" wifi.powersave 2   # 2 = 끔

  적용 후 10분 소크 결과 (3000 패킷, 0.2초 간격)

      손실 0.0%   min 5.889 / avg 8.858 / max 37.691 / stddev 1.957 ms

      100 ms 초과 (freeze 임계)      0 개
       33 ms 초과 (30Hz 한 프레임)   2 개  (37.7 / 37.0 ms)

  즉 **핫스팟도 30 Hz 제어 링크로 쓸 수 있는 수준입니다.** 최대 37.7ms 가
  한 프레임을 살짝 넘지만 지령이 절대값이라 다음 패킷이 덮어씁니다 —
  UDP 를 고르신 이유가 이 경우입니다.

  ★ 과신하진 않겠습니다. 10분은 40분 만에 터진 그 실패를 담기엔 짧고,
    지금은 폰이 가까이 유휴 상태에 5 GHz 입니다. 실제 지령 패킷으로 30분
    이상 돌려보고 §4-c 의 워치독 값을 확정하죠.

 5-3. 제안하는 역할 분담
--------------------------------------------------------------------------------
      제어 링크 (UDP 30 Hz)   **USB-C 직결**       1.16 ms / 편차 0.07 ms
      젯슨 인터넷             핫스팟               apt / git / uv
      원격·비상 경로          Tailscale            망이 달라도 접속

  ※ 젯슨에 Tailscale 이 이미 돌고 있습니다 (100.107.9.105). 12번 문서에
    나오는 Ubuntu 학습 서버와 같은 tailnet 이면 나중에 그대로 이어집니다.
    다만 Tailscale 은 오버레이라 망이 다르면 중계를 타므로 **제어 링크로는
    권하지 않습니다.** SSH·개발용으로는 최적입니다.

        can.Bus(interface="socketcan", channel="can0",       bitrate=1000000)
        can.Bus(interface="slcan",     channel="/dev/ttyACM0", bitrate=1000000)

    → 트랜시버 조달 가능 여부에 따라 정하겠습니다. 선택지가 하나 는 것입니다.

  ★ **현재 하드웨어는 아무것도 연결돼 있지 않습니다.**

        /dev/ttyACM*   없음   ← CAN 어댑터
        /dev/ttyUSB*   없음   ← 손 서보 어댑터
        /dev/video*    없음   ← 카메라

    §11 의 2단계(CAN 피드백 확인) 이후로는 아직 진행할 수 없습니다.
    소프트웨어(브리지 + 안전계층 + 테스트)를 먼저 끝내두겠습니다.
