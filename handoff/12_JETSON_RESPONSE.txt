 0. 한 장 요약
--------------------------------------------------------------------------------
  규격 잘 받았습니다. 결론부터 말씀드립니다.

   (1) **안 1(얇은 브리지)로 가겠습니다.** §4 프로토콜 그대로 구현합니다.
   (2) 젯슨 쪽에 **CAN 스택은 이미 만들어져 있고 실물 모터로 검증됐습니다.**
       DM4340 MIT 모드 인코딩, enable/disable, 피드백 디코딩(위치/속도/토크/
       온도/에러) 전부 동작 중입니다. 새로 만들 것은 UDP 계층과 안전계층뿐입니다.
   (3) **Q7 답: 토크·온도 됩니다.** DM4340 피드백 프레임 8바이트에 전부
       들어있고 이미 파싱하고 있습니다. err 코드도 실어 보내겠습니다.
   (4) **Q4 답: 손 서보 SCS0009 맞습니다.** 추정이 정확하셨습니다. 8개 ID 1~8,
       시리얼 1 Mbps로 구동 중입니다. 그리고 §2-3 의 서보각 배열이 저희 부호
       규약과 **완전히 일치합니다** (§5 에서 검증 결과 첨부).

  반대로 **합의가 필요한 것 4가지**가 있습니다. 이게 이 문서의 핵심입니다.

      A. enable=false 즉시 소자는 3-DOF 팔에서 위험합니다 → HOLD 상태 추가 제안
      B. seq 단조증가 규칙에 Mac 재시작 데드락이 있습니다 → session 필드 제안
      C. grasp 와 servo 필드가 중복입니다 → 우선순위 명시 필요
      D. 3번째 모터가 아직 없습니다 → 실물 준비 상태 확인 필요

  ★ 그리고 **네트워크는 지금 구성으로는 못 씁니다.** 실측 결과 §7-Q2 참고.

 Q1. 안 1 인가 안 2 인가
--------------------------------------------------------------------------------
    → **안 1 (얇은 브리지)** 로 가겠습니다.

    근거 3가지.

    (a) 젯슨에 CAN 계층이 이미 있습니다. 브리지 구현은 사실상 배선 작업입니다.
        - python-can + slcan 으로 DM4340 송수신 검증 완료
        - MIT 위치 명령 인코딩, enable/disable, 피드백 디코딩 전부 동작
        - 캘리브레이션(영점/가동범위/정규화) 계층도 이미 있음
        상세는 §2 참고.

    (b) placo / pinocchio 의 ARM64 지원을 확신할 수 없습니다.
        저희 프로젝트에도 pin>=3.7 을 kinematics 옵션으로 갖고는 있지만,
        **젯슨 배포 환경에는 설치하지 않고 있습니다.** aarch64 휠 존재 여부를
        검증한 적이 없어서 안 2 는 여기서 막힐 위험이 있습니다.
        (성능은 문제 없을 겁니다. Orin Nano 는 6코어 Cortex-A78AE 라
         30 Hz IK 는 여유입니다. 문제는 설치이지 연산이 아닙니다.)

    (c) 말씀하신 대로 실패 지점이 좁아집니다. 저희도 같은 이유로 동의합니다.

    ★ 다만 알려드릴 것이 있습니다.
      젯슨에는 **이미 별도의 Quest→WebXR→모터 파이프라인이 돌고 있습니다.**
      (다른 로봇 구성용: 2축 팔 + AmazingHand + LeRobot 데이터 기록,
       Vuer 로 젯슨이 직접 WebXR 서버를 띄우는 구조 — 즉 안 2 형태입니다.)

      두 파이프라인이 **같은 CAN 어댑터를 동시에 열면 충돌합니다.**
      배타 실행 규칙을 두겠습니다. 브리지 실행 중에는 기존 파이프라인을
      띄우지 않습니다. 그쪽에서 신경 쓰실 것은 없습니다.


 Q2. 네트워크 구성
--------------------------------------------------------------------------------
    → **지금 구성(폰 핫스팟)은 제어용으로 쓸 수 없습니다. 유선을 깔아야 합니다.**

    오늘 실측한 내용입니다. 같은 핫스팟에 Mac 과 젯슨을 붙여놓고 측정했습니다.

        [최초]      젯슨 발견 10.46.217.203 (DHCP 할당)
                    TCP 22 정상 접속, SSH 배너 수신 확인
        [약 40분 뒤] 같은 자리에서 아무 조작 없이 재측정
                    ping 30회 → **100% 패킷 손실**
                    TCP 22   → connection timed out
                    ARP 테이블에서 **엔트리 자체가 소멸**

    즉 아무 조작도 안 했는데 젯슨이 조용히 떨어졌습니다. 폰 핫스팟은
    유휴 클라이언트를 정리하고, 클라이언트 격리가 걸리기도 하며, DHCP 임대가
    갱신될 때 IP 가 바뀝니다. 30 Hz 제어 링크로는 부적합합니다.

    제안 (우선순위 순).

      1순위  **유선 직결.** 젯슨 Orin Nano 에 기가비트 RJ45 가 있습니다.
             Mac 은 USB-C 이더넷 어댑터. 그 사이에 랜선 하나.
             고정 IP 를 양쪽에 박습니다 (DHCP 없음, 링크로컬 아님).

                 Jetson  192.168.100.2 / 24
                 Mac     192.168.100.1 / 24

             → 지연 편차 최소, 끊김 없음, IP 가 절대 안 바뀝니다.
               "Mac 쪽 IP 가 계속 바뀌어서 고생 중"이라고 하신 문제도
               이걸로 같이 해결됩니다.

      2순위  전용 유선 공유기 + MAC 기반 고정 DHCP. Wi-Fi 는 관리용으로만.

      비추천 폰 핫스팟. 위 실측대로입니다.

    ★ 유선을 까시면 Wi-Fi 는 그대로 두고 인터넷/SSH 용으로 쓰시면 됩니다.
      제어 트래픽만 유선으로 분리하는 구성입니다.


 Q3. CAN 어댑터
--------------------------------------------------------------------------------
    → **USB-CAN 어댑터(CANable 계열), SLCAN 모드, 1 Mbps.**

        젯슨 장치 경로   /dev/ttyACM0
        python-can       interface="slcan", bitrate=1000000
        종단저항         버스 양 끝 120Ω (모터쪽 내장 여부 확인해서 조정)

    젯슨 Orin Nano 는 40핀 헤더에 네이티브 CAN 컨트롤러(mttcan)도 갖고 있지만
    외부 트랜시버가 필요해서 지금은 USB 어댑터를 쓰고 있습니다. 필요하면
    socketcan(can0)으로 바꿀 수 있고, 저희 코드는 인터페이스 문자열만
    바꾸면 되는 구조라 이관 비용은 없습니다.

    ※ 1 Mbps 는 3축 30 Hz 에는 과할 정도로 여유입니다. 500 Hz 보간(§7-Q6)을
      해도 문제없습니다.


 Q4. 손(AmazingHand)
--------------------------------------------------------------------------------
    → **SCS0009 추정이 맞습니다.** 붙일 수 있습니다.

        서보 수      8개 (ID 1 ~ 8)
        버스         시리얼(하프듀플렉스), **1 Mbps**
        젯슨 경로    /dev/ttyUSB* (USB-TTL 어댑터, 예: /dev/ttyUSB1)
        드라이버     rustypot 의 Scs0009PyController
        팔과의 관계  **완전히 별도 버스.** CAN 과 무관하게 독립 동작합니다.

    저희 쪽은 8서보를 sync_read / sync_write 로 한 번에 처리하고 있습니다.
    §2-3 의 서보각 규약이 저희 것과 일치하는지 대조했고, **일치합니다.**
    검증 내용은 §5 에 따로 정리했습니다. 꼭 봐주세요.

    ★ 「이번에 붙일지」는 [ 확 인 필 요 ] 로 남겨둡니다.
      팔 3축만 먼저 돌리고 손은 2차로 붙이는 쪽을 권합니다. 손을 빼면
      실패 지점이 하나 줄고, 붙이는 데 드는 추가 작업이 크지 않습니다.


 Q5. 팔 고정 방식

    base_link 가 프레임 원점보다 56.5 mm 아래로 내려간다는 것 확인했습니다.

 Q6. 30 Hz 로 충분한가
--------------------------------------------------------------------------------
    → **네, 충분합니다. 대신 젯슨에서 보간하겠습니다.** 말씀하신 방향에 동의합니다.

        Mac → 젯슨      30 Hz (지령)
        젯슨 → 모터     **500 Hz** (30 Hz 지령 사이를 선형 보간)

    보충. DM4340 의 MIT 모드는 위치+kp/kd 임피던스 제어라, 지령이 잠깐
    비어도 모터가 마지막 목표를 잡고 스스로 버팁니다. 실제로 저희 기존
    파이프라인은 30 Hz 로 직접 쏘고도 잘 돕니다.

    그럼에도 보간을 넣는 이유는 27 N·m 팔이기 때문입니다. 30 Hz 계단 입력은
    관절에 충격을 주고 진동을 유발합니다. 보간이 훨씬 부드럽습니다.
    Mac→젯슨 구간을 올리지 말자는 말씀에 전적으로 동의합니다.


 Q7. 토크/온도를 넣을 수 있나
--------------------------------------------------------------------------------
    → **전부 됩니다. 이미 파싱하고 있습니다.**

    DM4340 피드백 프레임 8바이트에 다음이 전부 들어있습니다.

        상태코드     4 bit   (아래 표)
        위치        16 bit   ±12.5 rad 로 스케일
        속도        12 bit   ±20 rad/s
        토크        12 bit   ±28 N·m
        MOS 온도     8 bit   °C
        로터 온도    8 bit   °C

    따라서 §4-3 상태 패킷의 q / dq / tau / temp / err 를 **전부 채워서**
    보내드릴 수 있습니다. 「없으면 생략 가능」한 필드가 하나도 없습니다.

    err 는 모터 상태코드를 그대로 싣겠습니다.

        0x0 정상(소자)    0x1 정상(여자)
        0x8 과전압        0x9 저전압        0xA 과전류
        0xB MOS 과온      0xC 코일 과온     0xD 통신 끊김     0xE 과부하

    ★ 부수적 교차검증: 저희 디코더의 토크 스케일이 **±28 N·m** 인데,
      §2-1 의 effort 가 **27 N·m** 입니다. 일치합니다. 같은 모터 맞습니다.
      (정격 9 / 피크 27 도 DM-J4340P-2EC 스펙과 맞습니다.)

 2. 젯슨이 이미 갖고 있는 것 (신규 개발 아님)

  「젯슨이 구현할 것은 딱 하나」라고 하셨는데, 그중 CAN 절반은 이미 있습니다.
  일정 산정에 참고하시라고 현황을 그대로 적습니다.

    [완성 · 실물 검증됨]
      · SLCAN USB-CAN 오픈 / 수신큐 드레인
      · DM4340 상태 조회 : 0x7FF 로 [id_lo, id_hi, 0xCC, 0…] 송신
                            → 피드백 ID(=명령ID+0x10)로 8바이트 수신
      · 피드백 디코딩 : 위치/속도/토크/MOS온도/로터온도/상태코드

      · MIT 위치 명령 인코딩 : pos16 + vel12 + kp12 + kd12 + tau12 비트패킹
      · 영점/가동범위 캘리브레이션 도구 (대화식, 파일로 저장)
      · 스텝당 이동량 제한 (=§5-3 속도 제한과 동일한 기능)
      · 연결 실패 시 역순 롤백 + 연결/해제 시 무조건 disable 선송신
      · AmazingHand 8서보 sync read/write
      · 카메라 2대 동시 취득

    [없음 · 이번에 새로 만듦]
      · UDP 5005 수신 / 5006 송신, JSON 직렬화
      · 워치독 (§5-1)            ← 지금은 UDP 링크 자체가 없어서 부재
      · 소프트 스타트 (§5-4)     ← 없음. 새로 만듭니다
      · 지령-실제 이격 제한 (§5-5)
      · 30 → 500 Hz 보간
      · TRIP 상태머신
      · 3번째 모터 (§4 참고)

  ★ 부탁: §9 의 src/rpo_teleop/motor_backend.py (SafetyLayer / SafetyLimits)
    와 tests/test_safety.py 를 보내주세요. 젯슨도 **Python 3.12 환경(uv)** 이라

 3. 합의가 필요한 것 (중요 · 여기가 이 문서의 핵심)
================================================================================

 3-A. enable=false 즉시 소자는 위험합니다 → HOLD 상태 추가 제안 [필수]
--------------------------------------------------------------------------------
    §4-2 에 「enable false → 즉시 소자」, 그리고 「★ 소자하면 팔이 중력으로
    떨어집니다」라고 직접 적어두셨습니다. 인지하고 계신 걸로 압니다.
    문제는 이게 **클러치를 놓을 때마다 일어난다**는 점입니다.

    §1-3 에 「Grip 을 떼면 그 자리에 정지」라고 되어 있는데, 소자로 구현하면
    그 자리에 정지하는 게 아니라 **툭 떨어집니다.** 27 N·m 급 40:1 감속기
    팔이면 사람이 다칠 수 있습니다.

    (참고로 저희 기존 2축 파이프라인은 grip 을 놓으면 실제로 소자합니다.
     그건 팔이 짧고 가벼워서 가능했던 선택이고, 이 팔에는 못 씁니다.)

    제안 : enable 불리언 대신 **모드 3단계**로 바꿉니다.

        "mode": "DISABLED"   토크 없음. 팔이 처짐. 받쳐놓고 쓸 때만.
        "mode": "HOLD"       토크 유지. **현재 실제 위치를 목표로 고정.**
                             q 필드는 무시. 클러치 뗀 상태의 기본값.
        "mode": "RUN"        토크 유지. q 를 추종.

    호환성. 기존 enable 불리언도 계속 받겠습니다.
        enable=true  → RUN
        enable=false → **DISABLED 가 아니라 HOLD 로 해석**
    소자가 정말 필요하면 mode="DISABLED" 를 명시적으로 보내주세요.
    「위험한 쪽이 기본값이 되지 않게」 하려는 것입니다.

    ★ 이게 §5-1 워치독과도 직결됩니다. 「100 ms 초과 → 현재 지령 유지(freeze)」
      는 토크가 살아있어야 성립합니다. HOLD 가 있어야 freeze 가 의미를 갖습니다.


 3-B. seq 단조증가 규칙에 재시작 데드락이 있습니다 [필수]
--------------------------------------------------------------------------------
    §4-2 : 「젯슨은 seq 가 이전보다 작거나 같으면 버립니다」

    Mac 쪽 프로세스를 재시작하면 seq 가 0 부터 다시 시작합니다. 그러면 젯슨은
    **영원히 모든 패킷을 버립니다.** 젯슨을 같이 재부팅해야 풀립니다.
    시운전 중 Mac 을 몇 번이나 재시작하실 텐데 매번 이러면 곤란합니다.

    제안 : 지령 패킷에 session 필드 추가.

        "session": 1754438400      // Mac 프로세스 시작 시각. 실행 중 불변

      젯슨 규칙
        session 이 바뀌면  → seq 추적을 리셋하고 새 세션 수락.
                             단 **상태를 HOLD 로 내리고** RUN 재요청을 기다림.
                             (재시작 직후 팔이 갑자기 움직이지 않게)
        session 이 같으면  → 기존대로 seq 역행 패킷 폐기.

    session 을 못 넣으시면 차선책으로 「seq 가 1000 이상 크게 역행하면
    재시작으로 간주」 규칙을 쓰겠습니다. 다만 명시적인 쪽이 훨씬 안전합니다.


 3-C. grasp 와 servo 필드가 중복입니다 [필수]
--------------------------------------------------------------------------------
    §4-2 패킷에 grasp(0~1 스칼라) 와 servo(8개 배열) 가 둘 다 있는데
    우선순위가 안 적혀 있습니다.

    제안 :
        servo 가 있으면      → servo 8개를 **그대로** 서보에 씀 (grasp 무시)
        servo 가 없거나 null → grasp 를 젯슨이 8개로 전개
        둘 다 없음           → 손 명령 없음. 마지막 위치 유지.

    그리고 인덱스 매핑을 명시적으로 확정해주세요.

        servo[0] → 서보 ID 1
        servo[1] → 서보 ID 2
        ...
        servo[7] → 서보 ID 8

    저희는 위와 같이 가정하고 §5 의 대조를 했습니다. 맞는지 확인 부탁드립니다.


 3-D. TRIP 해제 방법이 정의돼 있지 않습니다 [필수]
--------------------------------------------------------------------------------
    §4-3 에 「TRIP 해제는 사람이 명시적으로 해야 합니다 (자동 복구 금지)」라고만
    되어 있고 **수단**이 없습니다. 지금 규격대로면 젯슨을 재시작해야 풀립니다.

    제안 : 지령 패킷에 clear_trip 추가.

        "clear_trip": true

      젯슨 규칙
        · mode 가 DISABLED 또는 HOLD 일 때만 수락. RUN 상태에서는 무시.
        · 해제 후 상태는 반드시 **IDLE**. 바로 RUN 으로 안 갑니다.
        · 해제하려면 사람이 VR/대시보드에서 버튼을 누르는 걸로 해주세요.
          자동 재시도 루프에 넣으면 안 됩니다.
        · 해제 시 소프트 스타트 2초를 처음부터 다시 겁니다.


 3-E. 3번째 모터가 아직 없습니다 [확인 필요]
--------------------------------------------------------------------------------
    현재 젯슨에 캘리브레이션돼 있는 모터는 **2개**입니다.

        motor_0   명령 ID 0x01   피드백 ID 0x11
        motor_1   명령 ID 0x02   피드백 ID 0x12

    3-DOF 면 3번째가 필요합니다. 저희는 다음으로 할당할 계획입니다.

        joint3    명령 ID 0x03   피드백 ID 0x13

    [ 확 인 필 요 ] 3축 팔이 실물로 조립돼 있나요? 3번째 모터의 CAN ID 가
    공장 기본값(보통 0x01)이면 저희가 0x03 으로 바꿔야 합니다. 조립 상태와
    현재 ID 설정을 알려주시면 §6 캘리브레이션 일정을 잡겠습니다.


================================================================================
 4. §4 프로토콜 — 위 제안을 반영한 최종안
================================================================================

  전송 방식, 포트, JSON 한 줄, 30 Hz — **전부 동의합니다.** UDP 선택 이유
  (head-of-line blocking) 도 타당합니다. 아래는 §3 제안만 반영한 것입니다.

 4-1. 지령 패킷 (Mac → Jetson, UDP 5005, 30 Hz)
--------------------------------------------------------------------------------
    {
      "session":    1754438400,       // ★신규. Mac 프로세스 시작 시각, 불변
      "seq":        12345,
      "t":          1754438400.123,
      "mode":       "RUN",            // ★신규. DISABLED | HOLD | RUN
      "enable":     true,             // 하위호환. true=RUN, false=HOLD
      "q":          [0.9495, 1.4765, -0.0419],
      "grasp":      0.0,
      "servo":      [-0.61, 0.61, -0.61, 0.61, -0.61, 0.61, -0.61, 0.61],
      "clear_trip": false             // ★신규. RUN 중에는 무시
    }

    mode 와 enable 이 둘 다 있으면 **mode 우선**입니다.

 4-2. 상태 패킷 (Jetson → Mac, UDP 5006, 30 Hz)
--------------------------------------------------------------------------------
    {
      "session":   1754438400,        // 젯슨이 현재 수락 중인 세션 (에코)
      "seq":       12345,
      "t":         1754438400.130,
      "q":         [0.9481, 1.4702, -0.0418],   // 실제 관절각 (rad)
      "dq":        [0.01, -0.02, 0.00],
      "tau":       [1.2, 4.8, 0.03],
      "temp":      [38.0, 41.5, 36.0],          // MOS 온도
      "temp_rotor":[45.0, 49.0, 42.0],          // ★신규. 로터 온도(공짜라서 첨부)
      "err":       [0, 0, 0],
      "state":     "RUN",             // IDLE | RUN | HOLD | TRIP
      "trip":      null,
      "rx_age_ms": 33,                // ★신규. 마지막 지령 수신 후 경과(monotonic)
      "soft_start":1.0                // ★신규. 소프트스타트 진행률 0.0~1.0
    }

    q(실제값)는 반드시 보내라고 하셨는데, 동의합니다. 그리고 저희 쪽 §5-5
    이격 제한도 같은 값으로 판단하므로 **양쪽이 같은 근거로 판단**하게 됩니다.

    rx_age_ms 를 넣은 이유: Mac 쪽에서 링크 품질을 눈으로 볼 수 있게 하려는
    것입니다. 이 값이 튀기 시작하면 Wi-Fi 를 의심하시면 됩니다.

 4-3. 연결 절차 — §4-4 그대로 갑니다
--------------------------------------------------------------------------------
    1) 젯슨 부팅 → UDP 5005 리스닝, state="IDLE", 모터 소자
    2) Mac 이 mode="HOLD" 로 링크 확인
    3) Mac 이 상태 패킷의 실제 q 로 IK 시작점을 맞춤          ← ★
    4) Mac 이 mode="RUN" → 젯슨 여자, 소프트스타트 2초
    5) 조종 시작

    ★ 3) 을 빠뜨리면 팔이 홈으로 튄다는 지적, 정확합니다. 저희도 젯슨 쪽에서
      이중으로 막겠습니다. **여자 직후 첫 500 ms 동안은 지령 q 를 무시하고
      실제 q 를 목표로 유지**합니다. Mac 이 3)을 빠뜨려도 안 튀도록.


================================================================================
 5. §2-3 손 서보각 규약 대조 결과 — 일치합니다
================================================================================

  「반드시 서보각으로 명령하세요, 관절각으로 매핑하면 안 됩니다」라는 경고,
  저희 구현과 정확히 같은 판단입니다. 저희도 8서보 전송 계층과 grasp 매핑을
  분리해뒀습니다.

  저희 부호 규약은 이렇습니다.

      홀수 ID (1,3,5,7) → 논리각을 그대로
      짝수 ID (2,4,6,8) → 논리각의 **부호를 뒤집어서** 서보에 씀

  이걸 §2-3 배열에 대입해봤습니다 (servo[i] → ID i+1 가정).

      ID 1 (홀수, 부호 +) : 열림 raw -35 → 논리 -35
                            닫힘 raw +90 → 논리 +90
      ID 2 (짝수, 부호 -) : 열림 raw +35 → 논리 -35
                            닫힘 raw -90 → 논리 +90
      (ID 3~8 동일 패턴)

  → **8개 서보 전부 논리각 -35° ~ +90°.** 부호 교대 규약이 완전히 일치합니다.
    그쪽 배열을 저희 계층에 그대로 흘려넣을 수 있습니다.

  저희 기존 기본값은 열림 0° / 닫힘 110° 였는데, 이건 설정값이라 CLI 인자로
  바꾸면 끝입니다.

      hand_open_deg   = -35.0
      hand_closed_deg = +90.0

  즉 **손 쪽은 코드 수정 없이 설정만 바꾸면 붙습니다.**

  ※ 확인 부탁: servo[i] → ID i+1 매핑 (§3-C). 이 가정이 틀리면 위 결론이
    통째로 바뀝니다. 그리고 실물에서 서보 ID 가 1~8 로 세팅돼 있는지도
    조립 시 확인이 필요합니다.


================================================================================
 6. §6 부호/영점 표 — 현황과 절차
================================================================================

  「젯슨 쪽에서 채워서 돌려달라」고 하신 표입니다. 아직 못 채웁니다.
  3번째 모터와 실물 조립이 선행돼야 합니다 (§3-E). 현재 상태는 이렇습니다.

      관절     CAN ID   기어비   부호(+1/-1)   영점 오프셋(rad)   비고
      -------------------------------------------------------------------
      joint1   0x01     40:1     [ 미측정 ]    [  미측정   ]      기존 2축과 동일 ID
      joint2   0x02     40:1     [ 미측정 ]    [  미측정   ]      기존 2축과 동일 ID
      joint3   0x03     40:1     [ 미측정 ]    [  미측정   ]      ★모터 미할당

    ※ 현재 파일에 들어있는 오프셋 값은 **기존 2축 테스트 지그**의 것이라
      robot_arm_temp 에는 못 씁니다. 조립 후 전부 다시 잽니다.

 6-1. 저희 쪽 캘리브레이션 도구가 §6 절차와 동일합니다
--------------------------------------------------------------------------------
    대화식 도구가 이미 있습니다. 하는 일이 §6 절차와 같습니다.

      1) 세 관절 토크를 모두 끔
      2) 사람이 URDF 기본자세(전부 0)에 맞춰 놓고 ENTER  → 그때 엔코더값 = offset
      3) 사람이 각 관절을 전 가동범위로 움직인 뒤 ENTER  → 실측 min/max 기록
      4) 파일로 저장. 끝나도 **토크는 계속 꺼진 상태**로 둠

    ★ 중요: 이 절차는 **모터 플래시의 하드웨어 영점을 건드리지 않습니다.**
      전부 소프트웨어 오프셋입니다. 잘못 재도 다시 재면 그만이고,
      모터를 벽돌로 만들 위험이 없습니다.

 6-2. 부호(sign) 처리에 대한 확인 요청
--------------------------------------------------------------------------------
    저희 코드를 점검해보니 부호 반전이 정규화 계층([-100,100] 변환)에는
    있는데 **rad 계층에는 없습니다.** §4 프로토콜은 rad 로 주고받으므로
    rad 계층에 부호를 추가하는 작업이 필요합니다. 저희가 처리합니다.
    (그쪽에서 하실 것은 없습니다. 저희 쪽 작업 항목으로 기록해둡니다.)

    변환식은 주신 대로 씁니다.

        q_motor = sign × q_urdf + offset
        q_urdf  = (q_motor - offset) / sign

 6-3. 기어비 40:1 — 프로토콜에서 환산 불필요할 것으로 봅니다
--------------------------------------------------------------------------------
    §2-1 에 「감속비 40:1 이므로 출력축 기준으로 환산해서 주고받습니다」라고
    되어 있는데, 저희 판단으로는 **추가 환산이 필요 없습니다.**

    DM4340 피드백의 위치 필드를 저희는 ±12.5 rad 로 디코딩하고 있습니다.
    ±12.5 rad = ±716° 인데, 관절 가동범위가 ±178° (±3.11 rad) 이므로
    이 범위는 **출력축 기준으로 보면 자연스럽고, 모터축 기준이면 40배가
    모자랍니다.** 즉 모터가 이미 출력축 각도를 보고하고 있습니다.

    ★ 다만 이건 스펙 해석이고 실측이 아닙니다. 시운전 §6 절차 2)~3) 에서
      「관절을 눈으로 90° 돌렸을 때 피드백이 1.57 rad 만큼 변하는가」로
      교차검증하겠습니다. 40배 어긋나면 그때 바로 드러납니다.
      **영점을 맞추기 전에 전체 자세를 명령하지 말라**는 §6 경고를 지키면
      이 검증도 안전하게 됩니다.

 6-4. 미리 확인해야 할 모터 파라미터
--------------------------------------------------------------------------------
    저희 MIT 인코더는 다음 스케일을 가정하고 있습니다. 이 값이 모터 펌웨어의
    PMAX/VMAX/TMAX 설정과 다르면 **모든 명령이 조용히 잘못 스케일됩니다.**

        위치  ±12.5 rad      속도  ±20 rad/s      토크  ±28 N·m
        kp    0 ~ 500        kd    0 ~ 5

    시운전 첫 항목으로 모터 파라미터를 읽어서 대조하겠습니다. 저희 쪽
    체크리스트입니다.

    ※ 현재 kp=8.0, kd=0.5 를 쓰고 있는데 이건 기존 2축 지그 값입니다.
      27 N·m 팔에서는 재튜닝이 필요합니다. velocity_scale 0.1 로 시작하면서
      같이 잡겠습니다.

 7. §5 안전 요구사항 — 수용 여부
================================================================================

  「네트워크가 끊기면 Mac 은 아무것도 못 한다, 모터 옆에 있는 쪽이 멈춰야
  한다」— 전적으로 동의합니다. 전부 젯슨에서 구현합니다.

    5-1  워치독 100ms freeze / 500ms TRIP     수용. monotonic 시계 사용.
                                              ★ freeze 는 HOLD 전제 (§3-A)
    5-2  관절 한계 0.05 rad 마진               수용
    5-3  속도 제한 (velocity_scale 0.1 시작)   수용. 유사 기능이 이미 있음
    5-4  소프트 스타트 2초                     수용. 신규 구현
    5-5  지령-실제 이격 max(한스텝×5, 0.05)    수용. 신규 구현
    5-6  물리 비상정지                         수용. **전원 차단형**으로 답니다

  물리 비상정지는 신호선을 끊는 방식이 아니라 **모터 전원을 직접 끊는**
  래칭 버튼으로 하겠습니다. 소프트웨어가 통째로 죽어도 동작해야 하니까요.
  누른 뒤에는 손으로 돌려서 풀어야 복귀되는 타입입니다.

  ★ 젯슨이 추가로 넣을 안전장치 2가지 (그쪽 규격에는 없는 것)

    (a) 온도 TRIP. MOS 또는 코일 온도가 임계치를 넘으면 TRIP.
        모터가 에러코드로도 알려주지만 그 전에 저희가 먼저 자릅니다.
        임계치는 시운전 데이터를 보고 정하겠습니다.

    (b) 피드백 손실 TRIP. CAN 피드백이 연속 N회 안 오면 TRIP.
        모터가 살아있는지 모르는 채로 명령을 계속 쏘는 상황을 막습니다.

    3단계  모터 파라미터 대조          §6-4. PMAX/VMAX/TMAX
    4단계  영점·부호 캘리브레이션      §6. 관절 하나씩. 나머지는 소자+받침

    7단계  3관절 동시                  scale 0.1 → 0.3 → 이후

    9단계  손 부착 (선택)              §5 설정값 적용 후

  ★ 2~6단계는 **팔을 받쳐놓거나 최저 자세로 눕혀놓고** 합니다.
    소자 시 낙하를 전제하고 진행합니다.
